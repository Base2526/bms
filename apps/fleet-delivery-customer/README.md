# BMS Delivery Customer (Android/iOS debug shell)

This is a separate bare React Native Customer App shell for the synthetic quote-to-Delivery flow.
It does not share driver identity or credentials. Production activation is hard-disabled; only a
Debug build accepts the short-lived `customerActivation` generated by the local scenario runner.

Implemented:

- OS-keystore session storage using `WHEN_UNLOCKED_THIS_DEVICE_ONLY`;
- no caller-controlled tenant, branch or BMS order fields;
- motorcycle/small-package weight input, quote display and explicit Delivery confirmation;
- read-only current Delivery status through coarse match stages with no driver identity or location;
- strict server response parsing through `@bms/fleet-delivery-customer-core`;
- app-declared Android permission limited to `INTERNET`; the merged release manifest additionally
  contains only Keychain's biometric compatibility permissions and Android's app-scoped dynamic
  receiver permission;
- release cleartext networking disabled and release signing intentionally unconfigured;
- Delivery confirmation keeps a quote-bound idempotency key across network failure and restart;
  requests have a 15-second deadline, and search waits for recovery of the server's current Delivery.

Local Android emulator flow:

```bash
npm run dev:bootstrap
npm run dev:scenario -- customer-search
adb reverse tcp:4100 tcp:4100
cd apps/fleet-delivery-customer
npm ci
npm run android
```

Copy only `customerActivation.apiBaseUrl`, `.accessToken` and `.expiresAt` from the protected scenario
file into the Debug activation screen. Do not run `dev:customer-flow` for the same scenario first;
the app itself owns that quote/create flow. Recreate scenarios made before migration `0013`; their
older grants intentionally lack `TRACK` and are not widened in place. After the app reaches
`AWAITING_PAYMENT`, run this from
the repository root, then tap **รีเฟรชสถานะ** in the app:

```bash
npm run dev:customer-dispatch -- <scenario-id>
```

The runner uses separate service and driver tokens to simulate payment/readiness, start dispatch and
accept the offer. The Customer App never receives those authorities and should display
`จับคู่รถสำเร็จ`. Continue the same scenario with either synthetic path:

```bash
npm run dev:customer-complete -- <scenario-id>
# or
npm run dev:customer-return -- <scenario-id>
```

Refresh in the app to see coarse delivery/return stages. Neither runner uploads a photo, exposes GPS,
sends a notification, contacts a person or moves real money. When finished, clear the app session and run:

```bash
npm run dev:cleanup -- <scenario-id>
```

Local iOS Simulator flow (macOS/Xcode; no physical device or distribution signing):

```bash
cd apps/fleet-delivery-customer
npm ci
npm run ios:pods
npm start -- --port 8088
```

Keep Metro running and open another terminal in the same app directory:

```bash
npm run ios
# If multiple simulators are available:
xcrun simctl list devices available
npm run ios -- --udid <simulator-id>
```

The runner builds the Debug simulator target, boots/installs/launches it, and explicitly points it to
Metro on port 8088 (8081 may already belong to the BMS Docker stack). `--port` overrides that port;
`--no-build` reuses an existing Debug simulator build. Xcode embeds a **simulator-only** application
identity/Keychain access group and signs locally ad hoc. Building with `CODE_SIGNING_ALLOWED=NO`
can compile but cannot prove Keychain works at runtime. Device/Release signing remains unconfigured;
the simulator entitlement is scoped to Debug + `iphonesimulator` only. The runner avoids the pinned
React Native CLI's custom-build-directory/prebuilt-binary launch failures. The same API/scenario
steps above apply; iOS Simulator reaches `127.0.0.1:4100` without `adb reverse`.

Repository verification (builds both unsigned variants before checking the merged manifests):

```bash
npm run typecheck
npm run test:ci
npm run lint
npm run android:assemble
npm run ios:pods
npm run ios:build
npm run verify:native-boundary
npm audit --audit-level=high
```

Both Android and iOS native targets compile and display the same synthetic coarse-status projection.
The iOS target uses isolated Debug/Release bundle identifiers and contains no camera, location,
contacts or microphone usage key. Real payment, precise/live location, notifications, customer
contact, real POD bytes, production authentication, signed distribution and representative
real-device certification remain blocked external work.
