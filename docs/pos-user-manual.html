ระบบขายหน้าร้าน (POS)
สำหรับแคชเชียร์และผู้จัดการ

คู่มือนี้อธิบายการใช้งานหน้าจอ /pos ตั้งแต่เปิดกะ ขายสินค้า รับชำระเงิน คืนสินค้า จัดการเงินสดในลิ้นชัก ไปจนถึงปิดกะและออกรายงาน

หลักการสำคัญที่สุดของระบบนี้

เบราว์เซอร์ไม่เคยเป็นผู้กำหนดราคา — ราคา ส่วนลด อัตราแปลงแพ็ก และจำนวนสต็อก คำนวณจากเซิร์ฟเวอร์ทั้งหมด หน้าจอ POS แสดงตัวอย่าง (preview) เท่านั้น หากยอดที่หน้าจอกับเซิร์ฟเวอร์ไม่ตรงกัน บิลจะถูกยกเลิกทันทีด้วย PAYMENT_MISMATCH ไม่มีการปรับตัวเลขให้เข้ากันเงียบๆ

ระบุผู้ขายในทุกรายการ

ผู้ดูแลระบบสร้างเครื่องและออก Token ครั้งเดียวที่ /admin/pos-devices แล้วนำมาจับคู่ (pair) กับเบราว์เซอร์ หลังจากนั้นเครื่องจะจำ Token ไว้

PIN เก็บในหน่วยความจำเท่านั้น

PIN ของแคชเชียร์ไม่ถูกบันทึกลงเบราว์เซอร์ ทุกครั้งที่รีเฟรชหน้าหรือปิด-เปิดเครื่องใหม่ ต้องกรอก PIN อีกครั้ง — นี่คือพฤติกรรมที่ตั้งใจ ไม่ใช่ข้อบกพร่อง

บัญชี pos_only

บัญชีแคชเชียร์ที่ตั้งค่าเป็น pos_only จะถูกบล็อคจากการเข้า /admin ที่ระดับระบบ login ไม่ใช่แค่ซ่อนเมนู และบัญชีนั้นไม่สามารถปลดค่า pos_only ของตัวเองหรือของผู้ดูแลระบบได้

โครงหน้าจอเคาน์เตอร์

หน้าจอออกแบบสำหรับจอสูง 768px ซึ่งพื้นที่แนวตั้งเป็นทรัพยากรที่จำกัดที่สุด

  • แถบไอคอนซ้าย (68px) — สลับระหว่าง ขาย / คืนสินค้า / กะ / ตั้งค่า / รับสินค้า เฉพาะคอลัมน์ซ้ายเท่านั้นที่เปลี่ยนตาม
  • คอลัมน์ขวาอยู่คงที่เสมอ — ยอดรวม แป้นเงินสด และปุ่มชำระเงิน เพราะคิวลูกค้าซ้อนกันได้ (คนแรกยังจ่ายไม่เสร็จ คนถัดไปยื่นบิลมาคืนแล้ว)
  • หน้าเพจไม่เลื่อน — แต่ละคอลัมน์เลื่อนในกล่องตัวเอง ปุ่มชำระเงินจึงไม่ถูกดันตกจอเมื่อตะกร้ายาว
  • ออกจากแท็บขายแล้วกลับมา — โฟกัสจะกลับไปที่ช่องสแกนอัตโนมัติ
  • หน้าจอกว้างน้อยกว่า 768px แถบไอคอนจะย้ายลงเป็นแถบล่าง

จอแสดงผลสำหรับลูกค้า

เปิด /pos/display บนจอที่สองหันไปทางลูกค้า — แสดงรายการที่สแกน ยอดรวม ส่วนลด และเงินทอน โดยไม่มีปุ่มใดๆ เลย (เพราะลูกค้าเอื้อมมาแตะได้)

จอนี้ซิงค์ผ่าน BroadcastChannel ในเครื่องเดียวกัน ไม่ใช่ WebSocket — ถ้าอินเทอร์เน็ตร้านหลุด จอลูกค้าจะไม่ค้างแสดงยอดเก่าที่ผิด ไม่ต้องตั้งค่าอะไร ถ้าไม่เปิดหน้าจอนี้ก็ไม่มีผลกระทบใดๆ แสดงเฉพาะ 8 รายการล่าสุด

การขาย

ขายสินค้า

การสแกนและค้นหา

สแกนบาร์โค้ด พิมพ์ SKU หรือค้นหาจากรายการสินค้าสด ขายเป็นหน่วยย่อย (base unit) หรือเป็นแพ็กที่ตั้งค่าไว้ก็ได้

โหมดเครื่องสแกน (Scan Manager)

เครื่องสแกน Bluetooth คือคีย์บอร์ดในสายตาเบราว์เซอร์ ระบบจึง ไม่เดา ว่าเป็นการสแกนจากความเร็วการพิมพ์หรือจากช่องที่โฟกัสอยู่ แต่ละเครื่องตั้งได้ 2 โหมด

FOCUS โหมดพื้นฐาน

ใช้ช่องสแกนเดิม รองรับฮาร์ดแวร์ที่ตั้งค่าไม่ได้

ข้อจำกัด: ผู้ใช้ต้องคุมให้โฟกัสอยู่ในช่องที่ถูกต้องเสมอ

PREFIX โหมดแนะนำ

ตั้งค่าเครื่องสแกนให้ส่งปุ่มฟังก์ชัน (ปกติ F9) นำหน้า และ Enter ปิดท้าย

ระบบจะดักจับข้อมูลทั้งชุดก่อนที่ช่องสมาชิก PIN ชำระเงิน คูปอง หรือช่องข้อความใดๆ จะได้รับ

การสแกนถูกกำหนดโดยสถานะหน้าจอ ไม่ใช่โฟกัส

บริบทการสแกนที่แสดงบนหัวจอเป็นผู้ตัดสิน: แท็บ ขาย เพิ่มลงตะกร้า / ค้นหาสินค้า อ่านโดยไม่เพิ่ม / คืนสินค้า ค้นใบเสร็จ / รับสินค้า เพิ่มเข้าใบสั่งซื้อ — แท็บกะ ตั้งค่า หน้าต่างที่มีข้อมูลอ่อนไหว และช่วงที่กำลังเขียนข้อมูล จะปิดการสแกนทั้งหมด

พักบิล (Park)

ลูกค้าลืมของหรือหาบัตรไม่เจอขณะคิวยาว — กดพักบิลเพื่อรับลูกค้าคนถัดไป

  • บิลที่พักไว้ไม่จองสต็อกและไม่ล็อกราคา — เพราะการจองที่ลูกค้าไม่กลับมาจะค้างจนกว่าจะมีคนล้างด้วยมือ (ซึ่งในทางปฏิบัติคือไม่มีวัน) และบิลที่พักตอนเช้าไม่ควรขายราคาเช้าหลังปรับราคาตอนบ่าย
  • กดเรียกคืนบิลจะอ่านราคาจากรายการสินค้าใหม่ ถ้าสินค้าหมดจะขายไม่ผ่านด้วย INSUFFICIENT เหมือนบิลปกติ
  • บิลที่พักไว้จะหายไปพร้อมการปิดกะ ไม่ค้างข้ามวัน — จำกัด 20 บิลต่อกะ
  • สองเครื่องที่ใช้กะเดียวกันไม่สามารถดึงบิลเดียวกันมาขายซ้ำได้

Serial Number

สินค้าที่ตั้งค่า serial_tracked ต้องกรอก Serial 1 ตัวต่อ 1 หน่วยย่อย ก่อนขายจึงจะผ่าน — กล่องละ 10 ชิ้น 2 กล่องคือ 20 Serial ไม่ใช่ 2

  • ตรวจสอบ ก่อน สร้างบิล — กรอกไม่ครบจึงไม่เสียสต็อก ไม่หักแต้ม ไม่นับคูปอง
  • Serial ซ้ำในบิลเดียวกัน (แม้ต่างบรรทัด) หรือ Serial ที่ขายไปแล้วจะถูกปฏิเสธ
  • คืนสินค้าทั้งบิล — Serial กลับมาขายได้ใหม่ / คืนบางส่วนไม่ปลด Serial เพราะไม่มีบันทึกว่าชิ้นไหนถูกคืนมา การเดาจะทำให้ประวัติการรับประกันชี้ไปที่ชิ้นผิด
  • บังคับเฉพาะ POS เท่านั้น — ออนไลน์ไม่ได้ เพราะตอนลูกค้าสั่งไม่มีใครรู้ว่าจะหยิบชิ้นไหน คนแพ็กเป็นคนรู้

ค่าธรรมเนียมที่ไม่ใช่สินค้า

ค่าถุง ค่าบริการ ค่าห่อของขวัญ — เพิ่มเป็นบรรทัดพิเศษได้เลย ไม่ต้องสร้าง SKU ปลอม (ซึ่งจะทำให้มีสินค้าผีในคลังและทำรายงานสต็อกเสียหาย)

  • อยู่ในฐาน VAT — ค่าบริการที่เก็บโดยผู้ประกอบการจด VAT ต้องเสียภาษี
  • ลดราคาไม่ได้ — ส่วนลดทุกชั้นคิดจากยอดสินค้า ค่าธรรมเนียมบวกทีหลัง
  • บรรทัดที่ไม่ครบ (ไม่มีชื่อ ไม่มียอด หรือจำนวนไม่ใช่จำนวนเต็มบวก) จะถูกตัดออก ไม่ทำให้บิลล้ม — เพราะเคาน์เตอร์กดเพิ่มบรรทัดก่อนพิมพ์
  • ใช้สิทธิ์ pos.sell ก็เพียงพอ — เงินเข้าลิ้นชักที่ถูกนับตอนปิดกะ และชื่อรายการพิมพ์บนใบเสร็จให้ลูกค้าเห็น การมองเห็นนี้เป็นการควบคุมที่แน่นกว่าการล็อกสิทธิ์
การขาย

ราคาและโปรโมชั่น

ระบบมีกลไกราคาหลายชั้น ทุกชั้นคำนวณที่เซิร์ฟเวอร์และไม่นับเป็นส่วนลดตามบิล

ลำดับการหาราคา

POS การสร้างออเดอร์ ผลลัพธ์ AI และหน้าร้านออนไลน์ ใช้ลำดับเดียวกันทั้งหมด

ลำดับความสำคัญของราคา ราคา BASE ตามขนาด → ราคา BASE ร่วม → ราคาสินค้า (fallback)

การเว้นราคา override ตามขนาดให้ว่างจะกลับไปใช้ราคา fallback โดยไม่ลบข้อมูลสต็อกหรือประวัติแพ็ก

ราคาขายส่งตามจำนวน (Wholesale Steps)

"ซื้อสิบได้ราคาส่ง" — ขั้นที่มี min_qty สูงสุดที่ไม่เกินจำนวนซื้อจะชนะ และใช้กับ ทุกหน่วย ไม่ใช่เฉพาะหน่วยที่เกินเกณฑ์

บรรทัดที่ขายเป็นแพ็กจะใช้ราคาแพ็ก

แถวแพ็กคือการที่ร้านระบุตรงๆ ว่ากล่องนั้นราคาเท่าไร การให้สองกลไกแข่งกันในบรรทัดเดียวจะได้บิลที่อธิบายให้ลูกค้าไม่ได้ — หน่วยในแพ็กยังนับรวมเข้าเกณฑ์ SKU + ขนาดเดิม แต่ตัวบรรทัดแพ็กเก็บราคาแพ็กไว้

ขั้นราคาไม่จำเป็นต้องถูกลงเรื่อยๆ และระบบไม่แก้ให้ — ร้านที่คิดแพงขึ้นสำหรับยกลังเพราะต้องแพ็กพิเศษก็หมายความอย่างนั้นจริง หน้าที่ของระบบคือทำตามที่ตั้งค่าไว้อย่างคาดเดาได้ ไม่ใช่เดาเจตนาแล้วเลือกราคาถูกสุดให้เงียบๆ

โปรโมชั่น ซื้อ X แถม Y และ N ชิ้นราคาเดียว

โปรโมชั่นไม่ใช่ส่วนลดชั้นที่ห้า แต่เป็นกลไกราคาระดับบรรทัด และไม่อยู่ใต้เพดานส่วนลดตามบิล

เหตุผลที่ต้องแยกออกจากชั้นส่วนลด

ถ้าโปรโมชั่นอยู่ในชั้นส่วนลด โปรที่ร้านติดป้ายไว้บนชั้นวางอาจถูกตัดทอนเพราะบิลนั้นไปชนเพดาน — กลายเป็นร้านผิดคำพูดกับลูกค้าเพราะกฎภายในของตัวเอง ซึ่งอธิบายที่เคาน์เตอร์ไม่ได้ และใบเสร็จจะแสดงราคาเต็มพร้อมส่วนลดก้อนใหญ่ท้ายบิล ขณะที่ความเข้าใจของลูกค้าคือ "3 ชิ้น 100 บาท" คือ ราคาของสามชิ้นนั้น

เศษที่เหลือคิดราคาเต็มซื้อ 3 แถม 1 จำนวน 7 ชิ้น = ครบ 1 ชุด + 3 ชิ้นราคาเต็ม จ่าย 6 ชิ้น (ไม่เฉลี่ยราคาทุกหน่วย เพราะลูกค้านับของแถมได้)
จำนวนรวมข้ามขนาด คิดครั้งเดียวต่อ SKU ต่อบิล60ml สองชิ้น + 150ml สองชิ้น = สี่ชิ้นของสินค้านั้น ได้รับโปร (คิดแยกบรรทัดจะพลาดหรือคิดซ้ำ)
โปรที่แพงกว่าซื้อแยกจะไม่ถูกใช้ยอดที่ถูกกว่าชนะเสมอ — ป้องกันร้านลดราคาปกติต่ำกว่าราคาโปรของตัวเองแล้วระบบเก็บเงินลูกค้าแพงขึ้นในนามของโปรโมชั่น
1 สินค้า 1 โปรโมชั่นบังคับที่ระดับฐานข้อมูล เพราะสองโปรต้องตอบว่าอันไหนชนะ ซึ่งไม่มีคำตอบที่พนักงานอธิบายลูกค้าได้
มีช่วงวันที่โปรหมดอายุหยุดทำงานเอง ไม่ต้องรอใครจำมาแก้สินค้า — โปรค้างคือวิธีที่ร้านขายขาดทุนต่อเนื่องโดยไม่รู้ตัว
แพ็กไม่เข้าร่วมเหมือนขั้นราคาขายส่ง — แถวแพ็กระบุราคากล่องไว้แล้ว

ยังไม่รองรับ: โปรข้ามสินค้า ("ซื้อ A แถม B") เพราะไม่สามารถแสดงเป็นราคากลุ่มของ SKU เดียวได้

ตะกร้ารีเฟรชราคาก่อนชำระเงิน

ก่อนกดชำระเงินทุกครั้ง ระบบจะดึงราคา ขั้นขายส่ง ข้อมูลแพ็ก และโปรโมชั่นของทุกบรรทัดใหม่จากเซิร์ฟเวอร์

  • ถ้าผู้ดูแลระบบแก้ค่าใดหลังสินค้าเข้าตะกร้า — การชำระเงินจะหยุดก่อนเขียนออเดอร์ ยอดใหม่แทนยอดเดิม และแคชเชียร์ต้องตรวจและรับเงินอีกครั้ง
  • ขั้นขายส่งและโปรโมชั่นเป็นระดับ SKU — สแกนขนาดใดก็แทนที่ข้อมูลราคาของทุกขนาดของ SKU นั้นในตะกร้า ป้องกันขนาดหนึ่งใช้นโยบายเก่ากว่าอีกขนาด
  • สแกนซ้ำบรรทัดที่มีอยู่จะแทนที่ข้อมูลราคาด้วย ไม่ใช่แค่เพิ่มจำนวน
  • Preview สมาชิก คูปอง และแต้ม ผูกกับยอดที่ผลิตมันขึ้นมา — preview เก่าจึงไม่สามารถอนุมัติการชำระเงินหลังยอดตะกร้าเปลี่ยนได้

แต้มสะสม (Loyalty Points)

เรื่องกฎที่ระบบใช้จริง
การได้แต้ม เกิดใน transaction เดียวกับที่บิลเป็น PAID ทุกช่องทาง ฐานคิดคือยอดหลังหักส่วนลดทั้งหมด (ส่วนลดจึงไม่ทำให้แต้มพุ่ง) เฉพาะลูกค้าที่มี member_no — แค่มีประวัติใน CRM ไม่ได้แต้ม
การปัดเศษ ปัดลงเป็นหน่วยแลกเต็มหน่วยเสมอ เช่นอัตรา 100 แต้ม/หน่วย ยอด 3,045 แต้มแลกได้ 3,000 เหลือ 45 — ปุ่ม "ใช้ทั้งหมด" แสดงและส่ง 3,000 ที่ใช้จริง ไม่แสดง 3,045 ราวกับเศษจะหายไป
แลกไม่พอ = ปฏิเสธ ไม่ตัดทอน ขอแลกเกินที่มีหรือเกินที่บิลรับได้ บิลล้มด้วย POINTS_INVALID — การแลกน้อยลงเงียบๆ จะให้ส่วนลดน้อยกว่าที่ลูกค้าได้รับแจ้งและจ่ายเงินมา
คืนสินค้า ดึงแต้มที่ได้คืนและคืนแต้มที่แลกไป ตามสัดส่วนที่คืนเงิน — ถ้าไม่ทำ ซื้อ→ได้แต้ม→คืน จะกลายเป็นเครื่องผลิตแต้มฟรี
ยอดแต้มติดลบได้ ตั้งใจ — ลูกค้าที่คืนของหลังใช้แต้มไปแล้วจะติดลบ การบังคับเป็นศูนย์จะทำให้ "คืนของหลังแลกแต้ม" มีกำไร แต้มที่ได้ครั้งถัดไปจะไปชดเชยส่วนที่ติดลบก่อน
แต้มหมดอายุ FIFO ตามแถวที่ได้มา ขับด้วยงานประจำวัน — ถ้าไม่ตั้ง cron แต้มจะไม่หมดอายุเลย จนกว่ามีคนกดปุ่มที่ /admin/loyalty ตรวจได้ที่ /admin/operations-schedule
ยอดคงเหลือเป็นแคช bms_customers.points_balance เป็นแคชของผลรวม ค่า balanceMismatchCount ต้องเป็น 0 เสมอ — ถ้าไม่ใช่ /admin/loyalty จะขึ้นแบนเนอร์แดง
สำหรับฝ่ายบัญชี

แต้มที่ยังใช้ได้เป็น หนี้สิน (รายได้รอรับรู้ตาม IFRS 15) รายงานเป็นทั้งจำนวนแต้มและมูลค่าบาทตามอัตราแลกปัจจุบัน ให้ตัวเลขนี้กับนักบัญชีทุกสิ้นงวด — ไม่ใช่ตัวเลขตกแต่งบนแดชบอร์ด

สิ่งที่ตั้งใจไม่สร้าง

  • ไม่มีการแจ้งลูกค้าอัตโนมัติ — ไม่มีอะไรบอกลูกค้าว่าแต้มใกล้หมดอายุหรือเลื่อนระดับแล้ว หน้า /admin/loyalty แสดงรายชื่อสมาชิกที่แต้มจะหมดใน 30 วันให้ร้านติดต่อเอง นั่นคือกลไกทั้งหมด
  • ไม่มีรายงานแต้มแบบส่งออกไฟล์ — ตัวเลขแต้มเป็นการดูบนหน้าจอ ไม่ใช่ XLSX/CSV/PDF
  • แลกแต้มเป็นสินค้าไม่ได้ — แลกเป็นส่วนลดบิลเท่านั้น การแลกเป็นสินค้าต้องเคลื่อนสต็อกซึ่งเป็นอีกฟีเจอร์
  • AI อ่านยอดแต้มได้ แต่แลกไม่ได้ — การแลกเกิดตอนสร้างบิลเท่านั้น

บัตรของขวัญและเครดิตร้าน (Store Credit)

ใช้โครงบัญชีเดียวกับแต้ม — ยอดคือผลรวมของ ledger และคอลัมน์เป็นแคช

ต่างจากแต้มหนึ่งข้อ: เครดิตติดลบไม่ได้

แต้มติดลบได้เพราะการบังคับเป็นศูนย์จะทำให้คืนของหลังแลกแต้มมีกำไร แต่เครดิตคือเงิน และยอดติดลบหมายถึงร้านเป็นหนี้ลูกค้าโดยไม่มีใครอนุมัติ — บังคับด้วย CHECK ที่ตาราง ไม่ใช่แค่ในโค้ด

  • ตรวจรหัสก่อนสร้างบิล — รหัสผิดหรือยอดไม่พอจึงไม่เสียสต็อก ไม่เสียแต้ม ไม่นับคูปอง
  • ล็อกแถวบัตรตอนแลก — บัตรใบเดียวถูกสแกนที่สองเครื่องพร้อมกันได้ (ซื้อเป็นของขวัญแล้วใช้กันทั้งสองคน) ถ้าไม่ล็อกทั้งคู่จะอ่านยอดเก่าและใช้เกิน
  • STORE_CREDIT เป็นวิธีชำระเงิน แต่ไม่ใช่เงินสด — ร้านรับเงินไปแล้วตอนขายบัตร จึงต้องไม่เข้ายอดลิ้นชักหรือสูตรเงินสดคาดหวังตอนปิดกะ
  • คืนสินค้าคืนเครดิตกลับบัตรใบเดิม ตามสัดส่วนที่คืนเงิน — คืนบางส่วนเกิดได้หลายครั้งต่อบิล และแต่ละครั้งต้องคืนส่วนของตัวเอง
  • รหัสบัตรสุ่มจาก crypto ไม่ใช่เลขเรียง (GC-0001, GC-0002) เพราะบัตรของขวัญคือเงินที่ใครถือก็ใช้ได้ — เลขเรียงหมายถึงคนที่ซื้อหนึ่งใบเดาที่เหลือได้ทั้งหมด และตัดอักขระที่อ่านสับสน (I O 0 1) เพื่อบอกรหัสทางโทรศัพท์ได้
  • เครดิตค้างเป็นหนี้สิน เหมือนแต้ม — ให้นักบัญชีทุกสิ้นงวด

การออกบัตรและปรับยอดเป็นสิทธิ์ Manager เท่านั้น (เพราะเป็นการสร้างเงินขึ้นในระบบ) แต่การรับบัตรมาใช้เป็นสิทธิ์ของทุกคนที่ขาย เพราะเป็นงานปกติ

การปิดจะยกเลิกออเดอร์ที่ค้างและปล่อยสต็อกที่จองไว้ใน transaction เดียวกัน ไม่งั้นสินค้าจะยังขายไม่ได้หลังแถว OPEN หายไปแล้ว

มัดจำที่เปิดอยู่มีวันครบกำหนดและติดธง overdue เพราะสินค้าที่ถูกจองคือสินค้าที่คนอื่นซื้อไม่ได้ ถ้าไม่มีการมองเห็นนี้ ร้านจะสะสมสต็อกที่มีอยู่แต่ขายไม่ออกโดยไม่มีใครสังเกต

การแก้ไขบิล

คืนสินค้าและยกเลิกบิล

คืนสินค้าและยกเลิกบิลจบที่ผลลัพธ์เดียวกัน — ของกลับเข้าสต็อก เงินคืนลูกค้า แต้มถูกดึงคืน — แต่ความหมายต่างกัน และระบบแยกทั้งสองออกจากกัน

คืนสินค้า (Return)

การขายที่จบแล้วและลูกค้าเปลี่ยนใจ

  • เข้ารายงานการคืนสินค้า
  • คืนได้ทั้งบิลหรือบางส่วน
  • จำนวนที่คืนสะสมและเกินจำนวนที่ขายไม่ได้
  • ยอดคืนสุทธิใช้ส่วนลดระดับบิลของบิลเดิม
  • ต้องมีรหัสเหตุผล + รายละเอียด

ยกเลิกบิล (Void)

บิลที่ไม่ควรมีอยู่ตั้งแต่แรก — สแกนซ้ำ ผิดคน หรือเปลี่ยนใจก่อนออกจากเคาน์เตอร์

  • ถูกกรองออกจากรายงานการคืนสินค้าทั้ง 5 รายการ
  • เฉพาะบิลในกะที่ยังเปิดอยู่
  • เฉพาะบิลที่ยังไม่มีการคืนใดๆ
  • 2 คน 2 PIN ต้องมีผู้อนุมัติที่มีสิทธิ์ pos.void
  • เหตุผลเป็นข้อมูลบังคับ
เหตุผลที่ต้องแยก

การบังคับให้ Void เดินทางเส้นทางเดียวกับ Return ทำให้แคชเชียร์ที่พลาดวันละสองครั้งไปกระตุ้นสัญญาณเตือน "ความถี่การคืนสินค้าผิดปกติ" ทุกสัปดาห์ จนไม่มีใครเชื่อสัญญาณนั้นอีก — Void จึงใช้กลไก Return ทั้งชุด (สต็อก ล็อต แต้ม การจ่ายเงินคืน) แล้วติดธงแยก

ใบกำกับภาษีถูกยกเลิก ไม่ถูกลบ

เลขที่หายไปจากลำดับคือสิ่งแรกที่ผู้ตรวจสอบบัญชีถาม และไม่มีคำตอบที่ดี ระบบจึงบันทึก cancelled_at ไว้ บิลที่ Void จะออกจาก salesTotal และ billCount และปรากฏบนบรรทัดของตัวเองในรายงานกะ

เงินสดในลิ้นชัก

เงินเข้าออกลิ้นชักโดยไม่มีการขาย — ฝากธนาคารกลางกะ ยืมเงินทอนจากเครื่องถัดไป ซื้อน้ำแข็ง

อย่าบันทึกเงินจากการขายเป็นเงินสดเข้าลิ้นชัก

เงินจากบิลเงินสดที่ปิดแล้วถูกนับในเงินสดคาดหวังอยู่แล้ว การกรอกเงินนั้นอีกครั้งเป็นการบอกว่ามีเงินไหลเข้าจากภายนอกครั้งที่สอง ซึ่งทำให้ยอดคาดหวังเป็นสองเท่า

เงินสดเข้าแบบเดี่ยวใช้เฉพาะเงินที่เข้ามาจากนอกกระบวนการขาย เช่น เงินทอนที่เจ้าของเติม หรือโอนจากเครื่องอื่น — หน้าจอจะให้ยืนยันความเข้าใจข้อนี้อย่างชัดเจนก่อนบันทึก

เปิดลิ้นชักโดยไม่ขาย (No-Sale)

การเปิดลิ้นชักเพื่อแลกแบงก์ให้ลูกค้าเป็นเรื่องปกติ และห้ามไม่ได้ — ลิ้นชักทุกใบมีก้านปลดใต้ตัวเครื่อง ระบบที่ปฏิเสธจึงเพียงย้ายการกระทำไปที่ที่ไม่มีบันทึกเลย

  • บันทึกทุกครั้งพร้อมเหตุผลบังคับ และจำนวนครั้งปรากฏบนรายงานกะ — การพุ่งขึ้นของ No-Sale เป็นสัญญาณเก่าแก่ที่สุดอันหนึ่งในธุรกิจค้าปลีก
  • สิทธิ์ pos.nosale ให้ Manager, Sales และ Cashier — ไม่มีผู้อนุมัติโดยเจตนา เพราะการบังคับให้มีหัวหน้าทุกครั้งที่แลกเหรียญคือสิ่งที่ผลักพนักงานไปใช้ก้านปลด การควบคุมคือการบันทึก ไม่ใช่ประตู
  • ปุ่ม "เปิดลิ้นชัก" ในแท็บตั้งค่าที่เคยยิงสัญญาณโดยไม่บันทึกอะไร ถูกเปลี่ยนให้ชี้ไปแท็บกะ ที่ต้องมีเหตุผลและ PIN และลิ้นชักเปิดเป็นส่วนหนึ่งของการบันทึกเหตุการณ์

เอกสาร

ใบกำกับภาษีและใบเสร็จ

การตั้งค่าภาษี

การจดทะเบียน VAT อัตราภาษี วิธีปัดเศษ VAT ปีปฏิทินเอกสาร การอนุมัติใบกำกับอย่างย่อ และการปัดเศษเงินสด — ตั้งที่ /admin/pos-readiness (สิทธิ์ tax.setting.manage ทุกการเปลี่ยนแปลงบันทึก Audit พร้อมค่าก่อน/หลัง)

การตั้งค่าใช้กับบิลใหม่เท่านั้น — เอกสารที่ออกไปแล้วเก็บอัตราและยอดของตัวเองไว้บนแถวของมัน

ประเภท VAT ของสินค้า

ค่าความหมาย
Vสินค้าที่เสียภาษี
Nสินค้าที่ยกเว้นภาษี
UNKNOWNค่าเริ่มต้น — บล็อคการเปิดใช้งานสำหรับร้านที่จด VAT

แก้ได้รายสินค้าที่ /admin/products หรือตั้งทีเดียวทั้งหมดจาก /admin/pos-readiness

  • การไม่ส่งค่านี้มาจะเก็บค่าเดิมไว้ — ไม่งั้นการนำเข้าข้อมูลจำนวนมากหรือโค้ดที่เก่ากว่าฟีเจอร์นี้จะรีเซ็ตทุกสินค้าเป็น UNKNOWN ในการบันทึกครั้งถัดไป ล้างการจัดประเภทภาษีของร้านไปเงียบๆ (ค่าที่ระบบไม่รู้จักถือว่า "ไม่ได้ส่งมา" ด้วยเหตุผลเดียวกัน ไม่ใช่โยน error ล้มการนำเข้าทั้งไฟล์เพราะเซลล์เดียวผิด)
  • สินค้าใหม่เป็น UNKNOWN ไม่เดา — การตั้งเป็น V จะถูกส่วนใหญ่และผิดแบบมองไม่เห็นในส่วนที่เหลือ บนฟิลด์ที่ไปโผล่บนเอกสารภาษีที่ยื่นจริง
  • ปุ่มตั้งทีเดียวแตะเฉพาะแถว UNKNOWN และเฉพาะสินค้าที่ยังขายอยู่ — ร้านที่แยก V กับ N ถูกแล้วต้องไม่เสียงานนั้นไปเพราะกดปุ่มครั้งเดียว
  • ปุ่มตั้งทีเดียวใช้สิทธิ์ tax.setting.manage ไม่ใช่ product.edit — การจัดประเภทภาษีของสินค้าทั้งร้านไม่ใช่การตัดสินใจแบบเดียวกับการแก้ชื่อหรือราคาสินค้า

ใบเสร็จ

หน้าต่างพรีวิวเป็นการ์ดเดียว: หัวข้อบอกผลลัพธ์ (เลขเอกสาร ยอด วิธีชำระ เงินทอน) ตัวกระดาษใบเสร็จ และแถบปุ่ม

Enter พิมพ์ · Esc ปิด · ปุ่มเปิดลิ้นชักปรากฏเฉพาะเมื่อเชื่อมต่อเครื่องพิมพ์ ESC/POS ผ่าน WebUSB เพราะหน้าต่างพิมพ์ของเบราว์เซอร์เปิดลิ้นชักไม่ได้

ตัวเลขภาษีอ่านจากเอกสารที่ออกไปแล้ว ไม่คำนวณใหม่

ใบกำกับอย่างย่อเก็บฐานภาษี VAT และยอดยกเว้นของตัวเองไว้ การคำนวณ ยอด × 7/107 ใหม่จะพังทันทีที่บิลผสมสินค้ายกเว้นภาษี และลูกค้าจะถือหลักฐานที่ขัดกับสิ่งที่ร้านยื่น — ไม่มีเอกสาร ไม่มีบล็อก VAT

  • กระดาษของร้านที่จด VAT มีเลขประจำตัวผู้เสียภาษี การแยกยอดสุทธิ/VAT/สินค้ายกเว้น/การปัดเศษ และบาร์โค้ด Code 39 ของเลขเอกสารเพื่อสแกนกลับตอนคืนสินค้า
  • เลขผู้เสียภาษีมาจากโปรไฟล์ร้าน (/admin/settings) — เว้นว่างจะพิมพ์ใบเสร็จที่ไม่มีบรรทัด TAX# ซึ่งไม่ใช่ใบกำกับภาษีอย่างย่อที่ถูกต้อง
  • ใบคืนสินค้าและใบเปลี่ยนสินค้าไม่มีบล็อก VAT — ใบลดหนี้เป็นเอกสารแยก

ส่งใบเสร็จให้ลูกค้า

ส่งสำเนาทางอีเมลหรือ LINE ได้

  • การส่งที่ล้มเหลวไม่ทำให้การขายเสียหาย — การขายจบตอนรับเงิน อีเมลที่ตีกลับคือสำเนาที่ล้มเหลว ระบบจึงคืนผลลัพธ์ให้แสดง ไม่โยน error
  • อีเมลที่พิมพ์ที่เคาน์เตอร์ชนะข้อมูลในประวัติลูกค้า — พนักงานถามอีเมลด้วยปากตลอดเวลา และบิลอาจไม่มีลูกค้าผูกไว้เลย
  • อีเมลนั้นไม่ถูกเขียนกลับเข้าโปรไฟล์ลูกค้า — การพิมพ์อีเมลเพื่อรับใบเสร็จหนึ่งใบไม่ใช่การยินยอมให้เก็บข้อมูล

DISCOUNT_UNAPPROVED มีส่วนลดมือแต่ไม่มีผู้อนุมัติ+เหตุผล หรือ ยอดนั้นจะถูกเพดานต่อบิลตัดทอน ให้หัวหน้ากรอก PIN และเหตุผล / ลดยอดส่วนลดให้อยู่ในเพดาน แล้วคีย์ใหม่
POINTS_INVALID ขอแลกแต้มเกินที่สมาชิกมี หรือเกินที่บิลรับได้ — เกิดเมื่อยอดแต้มเปลี่ยนระหว่าง preview กับตอนชำระเงิน เรียกยอดใหม่ (re-quote) แล้วแจ้งลูกค้ายอดที่ถูกต้อง
WOULD_OVERDRAW รายการเงินสดจะทำให้เงินคาดหวังต่ำกว่าศูนย์ — มักเป็นการพิมพ์ผิด (฿99,999 แทน ฿999) ตรวจจำนวนหลักที่พิมพ์ (ระบบไม่บอกยอดจริงถ้าเปิด Blind Close)
ALREADY_RETURNED บิลนี้มีการคืนแล้ว — Void ทำได้เฉพาะบิลที่ยังไม่มีการคืนใดๆ ใช้การคืนสินค้าแทนการยกเลิกบิล
403 เงียบๆ ปุ่มกดแล้วไม่มีอะไรเกิดขึ้น — สิทธิ์นั้นยังไม่ถูก seed ตรวจว่า apply migration ที่ตั้งค่าสิทธิ์นั้นแล้ว (ดูตารางสิทธิ์ด้านบน)

เหตุผล

ถ้ามีอัตราปัจจุบันเดียว วันที่ร้านปรับ 2% เป็น 3% เดือนที่จ่ายไปแล้วทุกเดือนจะเปลี่ยนตัวเลขเงียบๆ พนักงานเปิดรายงานแล้วเห็นเลขที่ไม่ตรงกับสลิปเงินเดือนที่ได้ไป และไม่มีใครอธิบายหรือตรวจสอบได้

  • ความเฉพาะเจาะจงไล่จาก สินค้า → หมวด → ค่าเริ่มต้น ภายในช่วงวันที่มีผล
  • สินค้าที่คืนดึงค่าคอมกลับ — ถ้าไม่ทำ "ขายแล้วให้ลูกค้าคืนวันรุ่งขึ้น" จะกลายเป็นการปั๊มค่าคอม ซึ่งเป็นหนึ่งในการทุจริตที่สังเกตยากที่สุดเพราะทุกขั้นตอนดูถูกต้อง บิลที่ Void ไม่ได้ค่าคอมเลย
  • ส่วนลดระดับบิลถูกกระจายลงบรรทัด — ค่าคอมคิดต่อบรรทัดเพราะอัตราขึ้นกับสินค้าและหมวด บิลที่มีคูปองก้อนใหญ่จึงไม่จ่ายค่าคอมบนเงินที่ร้านไม่ได้รับ
  • commission.view และ commission.manage แยกกัน — หัวหน้าทีมควรอ่านตัวเลขของทีมได้โดยไม่สามารถขึ้นอัตราของตัวเอง
