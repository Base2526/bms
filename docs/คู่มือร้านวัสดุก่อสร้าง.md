## ภาพรวมและสถานะที่ต้องรู้

```text
ตั้งร้าน/สาขา/สิทธิ์ → ลง SKU + หน่วย + สต็อก → [ใบเสนอราคา] → ออร์เดอร์/POS
→ ชำระเงินหรือเปิดลูกหนี้ → ส่งมอบ/ส่งของ → คืนสินค้า/เอกสารภาษี → ตรวจรายงาน
```

ฐานข้อมูลและบริการฝั่ง server เป็นแหล่งจริงของราคา หน่วย ยอดเงิน สต็อก สิทธิ์ ลูกหนี้ และเอกสาร
`building_materials` เป็นเพียง **starter preset** ของคำแนะนำและลำดับเมนู; ไม่ได้เปิดความสามารถ
ชั่ง ตัด ส่งหลายเที่ยว หรือบัญชีเจ้าหนี้ให้เอง และประเภทร้านถูกล็อกหลังออร์เดอร์จริงแรก

| งาน | สถานะใน working tree | ขอบเขตที่ต้องจำ |
| --- | --- | --- |
| สินค้าทั่วไป แพ็ก lot/serial และ POS | มีบริการเดิม | ต้องตั้ง SKU, variant, stock policy, branch และสิทธิ์ให้ถูก |
| สเปกมีแหล่งอ้างอิง | Pilot | ฉบับร่างต้องมีผู้ตรวจอีกคนเผยแพร่; ช่องที่ไม่บันทึกคือ “ไม่ทราบ” |
| ชั่งน้ำหนัก prefix 22 ราคาต่อกก. | Pilot เฉพาะ retail POS | สต็อกเป็นกรัมจำนวนเต็ม; ต้องทดสอบเครื่องชั่งและคืนเงินจริง |
| ใบเสนอราคาโครงการ | Pilot | ไม่จองสต็อก; การกด SENT เป็นการบันทึกสถานะ ไม่ได้ส่งให้ลูกค้า |
| ขายเชื่อ/ใบแจ้งยอดภายใน | มี AR ledger; หน้าสรุปยอดเป็น pilot | หน้าสรุปไม่ส่งข้อความหรือออกเอกสารภาษี |
| PO รับบางส่วน / ส่งสินค้า | มี PO รับบางส่วนและตัวคูณหน่วยผู้ขายแบบ pilot; การส่งระดับทั้งบิล | ต้องตรวจหลักฐานผู้ขายจริง; ยังไม่มี ledger ส่งรายบรรทัดหลายเที่ยว |
| ตัดสายไฟจากม้วน, AP, ราคาก่อน VAT | ยังไม่รองรับครบ | ห้ามใช้ open-item หรือ expense evidence แทน workflow เหล่านี้ |

ตรวจว่ามี migration และสิทธิ์ใน **สภาพแวดล้อมที่ร้านจะใช้จริง** ก่อนเริ่ม pilot:
`10.133`–`10.137` เป็นงานใหม่ใน working tree นี้; ผลทดสอบบนฐาน throwaway ไม่ยืนยันว่า production
มีตารางหรือหน้าจอเหล่านั้นแล้ว

## ขั้นตอนที่ 1 — เตรียมร้าน สาขา และคน

**ผู้ทำ:** เจ้าของ/Administrator และผู้จัดการ · **เตรียม:** รายชื่อสาขา ผู้รับผิดชอบสินค้า คลัง
ใบเสนอราคา เครดิต ภาษี และเครื่อง POS

1. ที่ **Settings** (`/admin/settings`) ตรวจข้อมูลร้านและเลือก `building_materials` ก่อนบิลจริงแรก
   พร้อมตรวจนโยบายราคาและ VAT ของร้าน ค่าเริ่มต้นของ catalog/ใบเสนอราคาปัจจุบันคือ **ราคารวม VAT**
2. ที่ **Locations** (`/admin/locations`) สร้าง/ตรวจสาขาและยอดสต็อกตั้งต้นแยกสาขา
3. ที่ **Users / Permissions** (`/admin/users`, `/admin/permissions`) ให้สิทธิ์ตามหน้าที่
   แยกผู้ทำใบเสนอราคาจากผู้อนุมัติสเปก/ใบเสนอราคา
4. ที่ **POS Devices** (`/admin/pos-devices`) จับคู่เครื่อง ตั้ง PIN รายคน และลองเปิดกะทดสอบ
   เครื่องที่จับคู่แล้วไม่ใช่ตัวตนพนักงาน ทุกการขายยังตรวจ PIN กับสิทธิ์บน server

**ตรวจผล:** เปิดเมนูที่ได้รับสิทธิ์ได้ สาขาที่เลือกถูกต้อง คนไม่มีสิทธิ์ถูกปฏิเสธ
และมีผู้อนุมัติอีกคนพร้อมทำงาน · **ถ้าไม่ผ่าน:** ตรวจ role, branch scope, PIN และสถานะเครื่อง
ก่อนบันทึกยอดขาย ห้ามใช้บัญชีร่วมกัน

## ขั้นตอนที่ 2 — ลงสินค้า หน่วย สต็อก และสเปก

### 2.1 SKU, variant, หน่วย และแพ็ก

**ผู้ทำ:** ผู้ดูแลสินค้า (`product.edit`) · **เตรียม:** SKU, ขนาด/สีจริง, หน่วยนับฐาน,
ราคาขายรวม VAT, ต้นทุนที่ทราบจริง, VAT category, บาร์โค้ด, สาขา และจำนวนที่ตรวจนับแล้ว

1. ลง SKU ที่ **Products** (`/admin/products`) และกำหนด stock policy ให้ตรงลักษณะสินค้า
   สินค้าที่แยกนับทางกายภาพต้องมี variant/SKU และสต็อกแยก เช่น สี 1 ลิตรกับ 5 ลิตร
2. กำหนดหน่วยขายที่ **Product Packs** (`/admin/product-packs`) เมื่อมีการแปลงที่ตรวจได้จริง
   เช่น ปูนฐาน 1 ถุง, 1 พาเลท = 40 ถุง ระบุชื่อหน่วยที่จะพิมพ์บนใบเสร็จและราคาแพ็ก
   **อย่า** สร้างแพ็ก 5 ลิตรจากสี 1 ลิตรเพียงเพราะปริมาตรหารกันลงตัว
3. ตรวจ variant/barcode ที่ **Product Labels** (`/admin/product-labels`) และการเปิดขายตาม
   sales surface; บาร์โค้ดหนึ่งรหัสต้องชี้สินค้าหรือแพ็กที่ต้องการจริง
4. เครื่องมือที่ต้องระบุเลขเครื่องใช้ `SERIALIZED`; สินค้ามี lot/วันหมดอายุให้เปิด tracking
   ตามข้อเท็จจริง ไม่รวม lot ที่ไม่รู้ที่มาเข้ากับ lot เดิม
5. ตรวจสต็อกแยกสาขาใน Products หลังรับเข้าหรือนับสต็อก; ยอดจองดูได้จากบิลที่ถือสินค้า
   หากข้อมูลจองไม่ตรงระบบต้องให้ผู้จัดการตรวจ ไม่ลบ/แก้จำนวนเองเพื่อให้ตัวเลขดูตรง

**ตรวจผล:** ขาย 1 พาเลทแล้วตัด 40 ถุงของ SKU/variant/สาขาที่ถูกต้อง; สีคนละขนาด
และเลขเครื่องไม่ปะปนกัน · **ถ้าไม่ผ่าน:** หยุดขาย SKU นั้น ตรวจ pack factor, variant,
sales surface, barcode และ movement ก่อนแก้ข้อมูลสินค้า

> หน่วยที่นับสต็อก หน่วยที่ขาย หน่วยที่ตั้งราคา และหน่วยที่แสดงยังไม่มีสัญญา 4 หน่วยที่ครบ
> ทุกช่องทาง ห้ามให้หน้าจอรับเศษหน่วยฐานโดยหวังว่า backend จะเก็บเป็นทศนิยม

### 2.2 สเปกที่มีแหล่งอ้างอิง

**ผู้ทำ:** ผู้ดูแลสินค้า (`product.edit`) ร่าง และผู้ตรวจอีกคน (`product.spec.publish`) เผยแพร่
· **เตรียม:** เอกสารผู้ผลิตหรือหลักฐานที่ตรวจย้อนกลับได้

1. ที่ **Product Specs** (`/admin/product-specs`) เลือก SKU และ variant แล้วกรอกเฉพาะ
   ความยาว/กว้าง/เส้นผ่านศูนย์กลาง/ความหนาเป็นมิลลิเมตร น้ำหนักระบุเป็นกรัม เกรด มาตรฐาน
   และข้อจำกัดการใช้ที่เอกสารระบุจริง พร้อม `source reference`
2. กดบันทึกฉบับร่าง ผู้ตรวจอีกคนเปิด revision/แหล่งอ้างอิงแล้วกดเผยแพร่
3. ตรวจสถานะ `PUBLISHED`; ร่างใหม่ไม่แทนข้อเท็จจริงที่ลูกค้าเห็นจนกว่าจะเผยแพร่

**ตรวจผล:** SKU/variant และ revision ถูกต้อง ข้อความที่ไม่มีหลักฐานเว้นว่าง
· **ถ้าไม่ผ่าน:** หาหลักฐานเพิ่มหรือคงสถานะร่าง ห้ามใช้ชื่อสินค้า รูปภาพ หรือคำตอบ AI
เป็นหลักฐานยืนยันมาตรฐาน ความเข้ากันได้ หรือความปลอดภัยโครงสร้าง/ไฟฟ้า

## ขั้นตอนที่ 3 — ออกใบเสนอราคาโครงการ

**ผู้ทำ:** ฝ่ายขายสร้าง (`quotation.create`), ผู้อนุมัติอีกคน (`quotation.approve`),
ผู้มีสิทธิ์บันทึกส่ง/ยอมรับ/แปลง (`quotation.send/accept/convert`) · **เตรียม:** ลูกค้า CRM,
สาขา ชื่อโครงการ/หน้างาน รายการสินค้า variant หน่วย จำนวน ราคาที่ตกลง VAT ค่าส่ง และวันหมดอายุ

1. ที่ **Quotations** (`/admin/quotations`) กดสร้างร่าง เลือกลูกค้า สาขา โครงการ
   `PICKUP` หรือ `DELIVERY` และระบุหน้างานเมื่อส่งของ
2. ใส่รายการแต่ละบรรทัดเป็น SKU/size/pack/จำนวนเต็มของหน่วยขาย ตรวจราคาและส่วนลดที่ตกลง
   ราคารวม VAT และยอดแต่ละบรรทัดจาก server รายการไม่พบ ปิดขาย ราคาไม่ครบ หรือหน่วยผิด
   ต้องแก้ทั้งใบ ระบบไม่ควรข้ามบรรทัดที่ผิด
3. ถ้ายังไม่ทราบค่าส่ง ให้คงเป็น **ไม่ทราบ** ยอดรวมยังไม่ยืนยันและอนุมัติไม่ได้
   เมื่อทราบค่าส่งจึงกรอกและให้ผู้มีสิทธิ์คนละคนกด **Approve**
4. พนักงานกด **Send** เพื่อบันทึกสถานะหลังดำเนินการส่งตามกระบวนการร้าน
   ปุ่มนี้ **ไม่ส่งข้อความ/เอกสารให้ลูกค้าเอง** เมื่อได้รับคำตอบ ให้บันทึกหลักฐานการยอมรับ
   แล้วกด **Accept**; ถ้าลูกค้าไม่รับให้กด **Reject**
5. หากต้องแก้ใบที่มีแล้ว กด **Revise** เพื่อสร้าง revision ใหม่ ตรวจและอนุมัติใหม่
   ห้ามเขียนทับใบที่เคยอนุมัติ/ส่ง
6. กด **Convert** หลังลูกค้ายอมรับ ระบบตรวจวันหมดอายุ ราคา/ภาษี และสต็อกอีกครั้ง
   แล้วสร้างออร์เดอร์ผ่านบริการเดิม ถ้าสต็อกไม่พอหรือกฎไม่ผ่าน ใบยัง `ACCEPTED`
   ให้พนักงานแก้สาเหตุและทำรายการใหม่ตามสถานะที่ระบบอนุญาต

**ตรวจผล:** เลขเอกสาร/revision/สถานะ/วันหมดอายุตรงกัน ยอดออร์เดอร์หลังแปลงตรงกับ
ยอดอนุมัติ และสต็อกจองเฉพาะตอนสร้างออร์เดอร์ · **ถ้าไม่ผ่าน:** อ่านข้อผิดพลาดรายบรรทัด
หรือสถานะการแปลง ห้ามสร้างบิลใหม่มือเพื่อข้ามการตรวจและห้ามส่งยอดค่าส่ง 0 โดยไม่มีข้อตกลง

> ใบเสนอราคาไม่จองสินค้า ราคาที่ตกลงถูกตรึงเมื่ออนุมัติ และการแปลงต้องตรวจสต็อกซ้ำ
> เอกสาร PDF การส่งถึงลูกค้าและรูปแบบหลักฐานยอมรับยังต้องตรวจใน pilot จริง

## ขั้นตอนที่ 4 — ขายหน้าเคาน์เตอร์และสินค้าชั่ง

### 4.1 ขายสินค้าทั่วไป

**ผู้ทำ:** แคชเชียร์ (`pos.sell` + PIN) · **เตรียม:** กะเปิด สินค้า/แพ็กพร้อมขาย สต็อกสาขา
และวิธีรับเงินจริงที่ร้านเปิดใช้

1. เปิด `/pos` เลือก/สแกน SKU หรือบาร์โค้ด ตรวจ variant และแพ็กในตะกร้า
2. ตรวจยอดที่ server คำนวณและวิธีจ่าย เงินสด QR บัตร โอน หรือแบ่งจ่ายต้องรวมเท่ายอดบิล
   QR/บัตร/โอนต้องตรวจรับเงินจริงตามขั้นตอนร้านก่อนยืนยัน; สลิปที่อัปโหลดไม่ยืนยันเงินเอง
3. ยืนยันด้วย PIN แล้วดูใบเสร็จและยอดสต็อก บิลขายสำเร็จตัดสต็อก/lot และบันทึกเงินกับภาษี
   ใน transaction เดียว; ส่วนลดมือ void และเงินออกลิ้นชักต้องมี PIN ผู้อนุมัติอีกคน

**ตรวจผล:** จำนวนที่ตัดเป็นหน่วยฐานของ SKU/variant/สาขาที่ถูกต้อง ยอดบนใบเสร็จตรงยอดชำระ
· **ถ้าไม่ผ่าน:** อย่ากดซ้ำด้วย key ใหม่ทันที ตรวจประวัติบิลก่อน retry

**เมื่อรับมัดจำ:** ใช้ workflow Deposit/Layaway บน POS แทนการทำบิลขายเชื่อ
เงินมัดจำครั้งแรกต้องน้อยกว่ายอดบิล ออร์เดอร์ยัง `PENDING` และสต็อกถูกจอง
เมื่อรับยอดที่เหลือให้กด settle ที่สาขาที่จองสินค้า ระบบจึงตัดสต็อกและออกเอกสารภาษี
ตามกฎเดิม; สินค้ามี serial ให้บันทึกเลขเครื่องจริงตอนส่งมอบ ไม่ใช่ตอนเปิดมัดจำ
การปิดมัดจำที่ไม่มารับต้องมีเหตุผลและคืนสต็อกจอง ส่วนเงินที่ต้องคืนให้ทำผ่านทางคืนเงิน
แยกต่างหาก ตรวจยอดคงเหลือและกะที่รับเงินจริงก่อนยืนยันทุกครั้ง

### 4.2 ชั่งน้ำหนักพร้อมฉลาก prefix 22 — pilot

**ผู้ทำ:** ผู้จัดการเผยแพร่ราคา (`product.weighted_price.publish`), แคชเชียร์ขาย
(`pos.sell` + PIN) · **เตรียม:** SKU/variant แบบ `WEIGHTED` ฐานกรัม, รหัสเครื่องชั่ง 5 หลัก
และ size ที่ตรงสินค้าใน **Stock Models** (`/admin/stock-models`), เครื่องชั่งที่พิมพ์ฉลาก
prefix 22 ตามรูปแบบที่ร้านตั้ง, สต็อกกรัมจำนวนเต็ม และราคาขายรวม VAT ต่อกิโลกรัม

1. ผู้จัดการเปิด **Weighted Prices** (`/admin/weighted-prices`) เลือกสินค้า/variant
   ใส่อัตราเช่น `23.45` บาท/กก. แล้วตรวจและกด Publish
2. ชั่งสินค้าจริง สแกนฉลาก prefix 22 ที่มี checksum ถูกต้องที่ POS และตรวจกรัมที่หน้าจอ
3. ตรวจยอดบิลหลังระบบคำนวณจากราคา/กก. และกรัมบนฉลาก server จะถอดฉลากซ้ำตอนบันทึก
   และเก็บ rate/basis/rounding ใน snapshot; ยอดเงินบรรทัดเป็นหลัก

**ตรวจผล:** ฉลากหนึ่งใบตรง SKU และน้ำหนักจริง บิลเก็บยอดเป็นสตางค์และสต็อกลดเป็นกรัมเต็ม
· **ถ้าไม่ผ่าน:** หยุดขาย ตรวจฉลาก mapping เครื่องชั่งและราคา อย่าพิมพ์ราคาที่ client ส่งมา
แทนผล server รูปแบบ prefix 21 และการขายอัตรานี้ผ่านเว็บ/AI ลูกค้ายังไม่รองรับ

## ขั้นตอนที่ 5 — ขายเชื่อและติดตามยอด

**ผู้ทำ:** ผู้จัดการตั้งบัญชี (`ar.manage`), ผู้มีสิทธิ์อนุมัติขายเชื่อ (`ar.sell`),
ผู้รับชำระ (`ar.collect`), ผู้ตรวจยอด (`ar.view`) · **เตรียม:** ลูกค้า CRM, วงเงิน,
จำนวนวันเครดิต, บัญชี `ACTIVE` และกะเปิดหากรับเงินสด

1. ที่ **Receivables** (`/admin/receivables`) ตั้งบัญชีลูกค้า วงเงิน และเทอม
   บัญชีใหม่เริ่มวงเงิน 0 จึงต้องอนุมัติวงเงินจริงก่อนขาย
2. ที่ POS เลือกวิธีชำระ `CREDIT` เต็มจำนวนหรือร่วมกับเงินสด/วิธีอื่น
   ระบบตรวจวงเงินภายใต้ transaction; แคชเชียร์ที่ไม่มี `ar.sell` ต้องให้ผู้มีสิทธิ์ใส่ PIN
3. เมื่อรับชำระหนี้ บันทึกที่หน้ารับชำระตามวิธีจริง เงินสดต้องทำที่เครื่อง/กะที่รับเงินจริง
   ไม่ลงเงินสดในหลังร้านที่ไม่มีกะ ระบบจัดสรรหนี้เก่าก่อนและไม่รับยอดเกินหนี้
4. กดดู **ใบแจ้งยอดภายใน** ของบัญชีที่ Receivables ตรวจยอดจาก AR ledger,
   หนี้เกินกำหนด รายการรับชำระ/เครดิต และคำเตือนหากยอด cache ไม่ตรง ledger

**ตรวจผล:** หนี้ลดตามยอดที่รับจริง การคืนบิลเครดิตลดหนี้/เกิดเครดิตลูกค้าตาม ledger
· **ถ้าไม่ผ่าน:** หากมี mismatch หรือรายการถูกตัดทอน ให้ฝ่ายการเงินตรวจ ledger
ห้ามส่งใบแจ้งยอดนี้เป็นเอกสารภาษีหรือใช้แจ้งเตือนลูกค้าอัตโนมัติ

## ขั้นตอนที่ 6 — ซื้อเข้า ส่งของ คืนสินค้า และภาษี

### 6.1 PO และรับบางส่วน

**ผู้ทำ:** จัดซื้อ (`purchase.edit`) และผู้รับสินค้า (`purchase.receive`)
· **เตรียม:** supplier, SKU/variant, จำนวนในหน่วยฐานที่ระบบรับได้, ต้นทุน,
lot/expiry หากสินค้าเปิด tracking

ที่ **Purchase** (`/admin/purchase`) สร้าง PO ตรวจบรรทัด เลือกสาขาที่มีสิทธิ์รับ แล้วกดรับจำนวนที่มาจริง
PO เปลี่ยน `OPEN → PARTIAL → RECEIVED`; การรับซ้ำด้วย key เดิมต้องได้ผลเดิม
ตรวจยอดสต็อกและ movement หลังรับแต่ละครั้ง หาก supplier ส่งเป็นหน่วยอื่น เช่น พาเลท
ให้ระบุจำนวนหน่วยฐาน จำนวนพาเลท ตัวคูณ และหลักฐานจากผู้ขายที่ตรวจแล้วในบรรทัด PO
ตัวอย่างสมมติ: 2 พาเลท × 40 ถุง = 80 ถุง และต้นทุนที่กรอกยังเป็นต่อถุง
PO ที่แปลงหน่วยต้องระบุต้นทุนต่อถุงชัดเจน; ระบบไม่ตีความต้นทุนที่ไม่ทราบเป็นศูนย์
หากพนักงานมีสิทธิ์หลายสาขาต้องเลือกสาขาก่อนรับ; หากมีสาขาเดียวระบบเลือกให้
แต่ server ยังตรวจสิทธิ์สาขาซ้ำ ถ้าไม่มีสิทธิ์จะปฏิเสธโดยไม่เปลี่ยนสต็อก
ส่วน POS ผูกสาขาจากอุปกรณ์ที่จับคู่ไว้
ตอนรับบางส่วนให้กรอกจำนวนพาเลทที่มาจริง ระบบตรวจจำนวนถุงฐานกับตัวคูณที่ตรึงไว้
และปฏิเสธทั้งรายการหากไม่ตรงกัน การรับครึ่งพาเลทหรือหน่วยที่แบ่งไม่ได้ต้องออก PO
เป็นหน่วยฐานที่ถูกต้องใหม่ ห้ามเปลี่ยนตัวคูณบน PO เดิมเพื่อให้ยอดผ่าน
workflow นี้ยังเป็น **pilot** ที่ต้องเทียบฉลากและใบส่งของจริง และยังไม่รองรับ
ราคาจากใบกำกับต่อพาเลทที่หารเป็นต้นทุนต่อถุงไม่ลงตัวแบบอัตโนมัติ การคืน supplier,
เจ้าหนี้การค้า/จับคู่ PO-ใบรับ-ใบกำกับ-จ่ายเงิน และต้นทุนขนส่งเข้ายังไม่ครบ

**ถ้าไม่ผ่าน:** หยุดรับเมื่อ lot หรือจำนวนไม่ตรง ตรวจหลักฐานจริงก่อนลองใหม่
อย่าใช้ expense evidence แทนเจ้าหนี้โดยไม่เปิด workflow บัญชีจริง

### 6.2 ส่งของและรับที่สาขา

**ผู้ทำ:** ฝ่ายขาย/คลัง (`order.ship`) · **เตรียม:** ออร์เดอร์ สาขา ปลายทาง/หน้างาน
และหลักฐานการส่งมอบตามนโยบายร้าน

ที่ **Orders** (`/admin/orders`) ตรวจออร์เดอร์และที่อยู่หน้างานก่อนยืนยันส่ง
ใบเสนอราคาที่แปลงเป็น `PICKUP` ใช้การยืนยันรับที่สาขาแยกจาก shipment ของร้านอาหาร
และตัดสต็อกครั้งเดียว; `DELIVERY` ใช้การเปลี่ยนสถานะออร์เดอร์เดิม
ปัจจุบันเป็น **ทั้งบิล** เท่านั้น การส่งหนึ่งบิลหลายเที่ยว การจอง/ส่ง/ค้างรายบรรทัด
รถ คนขับ น้ำหนักบรรทุก ค่าแรงยก รถยก และ proof of delivery ยังไม่มี ledger รองรับ
หากต้องส่งหลายเที่ยว ให้หยุด pilot และกำหนดกระบวนการเอกสารภายนอกกับร้านก่อน
ไม่กด `SHIP` เพื่ออ้างว่าส่งครบทั้งที่ยังค้างของ

### 6.3 คืนสินค้าและเอกสารภาษี

**ผู้ทำ:** ผู้มีสิทธิ์คืนสินค้า/คืนเงิน (`pos.return`, `payment.refund` ตามขั้นตอน)
และผู้ออกเอกสาร (`tax.document.issue`) · **เตรียม:** บิลเดิม จำนวนที่คืน
เลข serial/lot เดิม เหตุผล และวิธีคืนเงิน

ที่ POS เลือกบิลเดิมและจำนวนที่คืน ระบบอ้างราคาขาย snapshot เดิมสำหรับการคืนบางส่วน
และตรวจ lot ก่อนรับกลับ ถ้า lot ต้นทางไม่ทราบหรือชนข้อมูลเดิม ระบบปฏิเสธด้วย
`STOCK_REVIEW_REQUIRED`; ห้ามรับเข้าสต็อกพร้อมขายโดยเลี่ยงข้อผิดพลาด
คืนข้ามสาขาต้องมี `pos.return.cross_branch` และ PIN ผู้อนุมัติอีกคน สต็อกที่รับคืนเข้า
สาขาที่รับของจริง ส่วนเอกสารยังอ้างบิลขายเดิม; การคืนข้ามวันบันทึกตามวันคืนจริง
เงินสดคืนทันที ส่วน QR/บัตร/โอนรอผู้มีสิทธิ์บันทึกการคืนเงินภายนอก
บิลที่มีเอกสารภาษี active ต้องทำตามทางแก้เอกสารที่ระบบอนุญาตก่อนยกเลิก/คืน
ราคารวม VAT เป็นสัญญาปัจจุบัน; รูปแบบ “ราคาก่อน VAT + VAT” สำหรับ B2B ยังไม่ครบทุกช่องทาง
ให้ผู้เชี่ยวชาญภาษีตรวจรูปแบบเอกสารก่อนใช้ยื่นจริง

## แชทและเว็บ

AI ลูกค้าอ่านได้เฉพาะสินค้า ราคา หน่วย สต็อก และสเปกที่เผยแพร่ผ่าน tool ที่อนุมัติ
ข้อมูลไม่ทราบต้องตอบว่าไม่ทราบ ไม่คำนวณความปลอดภัยโครงสร้าง/ไฟฟ้า ปริมาณเผื่อเศษ
ความเข้ากันได้ ค่าแรงยก รถยก หรือเที่ยวส่งจากการเดา ใบเสนอราคาที่อนุมัติ
เครดิต คืนเงิน และแก้สต็อกเป็นงานพนักงานมีสิทธิ์ยืนยัน

ตะกร้าเว็บทั่วไปให้ server ทบทวนราคา/แพ็ก/สต็อกอีกครั้งก่อนสั่ง แต่ pilot ราคาชั่ง
ต่อกิโลกรัมยัง **ปิดการขายผ่านเว็บและ customer AI**; อย่าคัดลอกราคา/กรัมจาก catalog
ไปตอบเป็นราคา/กก. สลิปที่ลูกค้าอัปโหลดคง `PENDING` จนพนักงานยืนยันเงิน

- [ ] ตรวจใบเสนอราคาที่รออนุมัติ ค่าส่งที่ยังไม่ทราบ และวันที่หมดอายุ

### ระหว่างวันและปิดวัน

- [ ] เทียบรายการขายกับเงินสด/QR/บัตร/โอนและหนี้เครดิต ไม่รวมเครดิตเป็นเงินลิ้นชัก
- [ ] เทียบ PO รับจริงกับ stock movement และแก้ lot ที่ต้องตรวจ
- [ ] ตรวจออร์เดอร์ค้างส่ง อย่ากดส่งครบเมื่อของยังค้าง
- [ ] ตรวจใบคืน/คืนเงินค้าง ผู้อนุมัติ และเอกสารภาษีที่เกี่ยวข้อง
- [ ] ปิดกะและตรวจ AR ledger/ยอด mismatch ก่อนนำตัวเลขไปใช้บัญชี

## สิทธิ์และการแก้ปัญหา

| งาน | สิทธิ์หลัก | หมายเหตุ |
| --- | --- | --- |
| ดู/แก้สินค้าและแพ็ก | `product.view` / `product.edit` | ต้องอยู่ใน tenant/branch ที่อนุญาต |
| ร่าง/เผยแพร่สเปก | `product.edit` / `product.spec.publish` | คนเผยแพร่ต้องไม่ใช่คนร่าง revision เดียวกัน |
| เผยแพร่ราคา/กก. | `product.weighted_price.publish` | ต้องยืนยันราคาและ sales surface |
| ใบเสนอราคา | `quotation.view/create/approve/send/accept/convert` | ผู้เตรียมอนุมัติใบตนเองไม่ได้ |
| POS/เครดิต | `pos.sell`, `ar.sell`, `ar.collect`, `ar.view`, `ar.manage` | PIN และกะ/อุปกรณ์ตาม action |
| PO/ส่งของ/ภาษี | `purchase.edit/receive`, `order.ship`, `tax.document.issue` | ต้องตรวจสาขาและ confirmation |

**ปัญหาที่พบบ่อย**

- **ไม่เห็นเมนู:** ตรวจสิทธิ์ role, สาขา, migration และว่า feature เป็น pilot ใน environment นี้หรือไม่
- **ใบเสนอราคาอนุมัติไม่ได้:** ตรวจค่าส่งที่ยังไม่ทราบ, หน้างาน, VAT category,
  วันหมดอายุ, ราคาที่รองรับ และว่าผู้อนุมัติไม่ใช่ผู้ร่าง
- **แปลงใบเสนอราคาไม่ได้:** ตรวจ stock/pack/สินค้า active ณ เวลาแปลงและยอดภาษี
  อย่าถือว่าการอนุมัติใบได้จองสินค้าแล้ว
- **สแกนฉลากชั่งไม่ได้:** ตรวจ prefix 22, check digit, รหัสสินค้า/variant, อัตราที่เผยแพร่
  และหน่วยกรัม; prefix 21 ยังไม่ใช่ทางขายนี้
- **คืนสินค้าแล้วขึ้น `STOCK_REVIEW_REQUIRED`:** ตรวจ lot/serial ต้นทางและส่งผู้รับผิดชอบ
  ห้ามกดรับเข้าแบบอื่นเพื่อให้ยอดผ่าน
- **ยอดลูกหนี้ไม่ตรง:** เปิดใบแจ้งยอดภายใน ตรวจ ledger กับ cache และรายการตัดทอน
  หยุดใช้ยอดนั้นทำรายงานบัญชีจนตรวจสาเหตุ

## ข้อจำกัดก่อนใช้กับร้านจริง

1. ยังไม่มีงานตัดต่อเมตรจากแท่ง/ม้วนที่บันทึกเศษดี เศษเสีย ต้นทุนและคืนใน transaction เดียว
2. ยังไม่มีการส่งบางส่วนรายบรรทัด/หลายเที่ยว รถ คนขับ ข้อจำกัดบรรทุก หรือหลักฐานส่งมอบ
3. PO รับบางส่วนและตัวคูณหน่วย supplier เป็น pilot ที่ต้องเทียบหลักฐานจริง; supplier return,
   AP ledger, การจับคู่เอกสารสามทางและการปันส่วนต้นทุนต่อแพ็กยังต้องทำ/พิสูจน์
4. ราคา “ก่อน VAT + VAT” แบบ B2B ยังไม่ใช่สัญญาราคาทุกช่องทาง เอกสารภาษีต้องให้นักบัญชีตรวจ
5. Pilot สเปก ราคา/กก. ใบเสนอราคา และ AR statement ยังต้องทดสอบ UI ที่ล็อกอินจริง,
   คน/สาขาจริง เครื่องชั่ง/สแกน/พิมพ์จริง และเงิน/คืน/ภาษีครบวงจร
6. Carrier/marketplace ไม่มีสัญญาและ credentials ที่พิสูจน์แล้วต้องคงสถานะ pilot/scaffold
