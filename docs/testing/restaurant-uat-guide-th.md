# คู่มือข้อมูลตัวอย่างและการทดสอบร้านอาหาร BMS

ครอบคลุม 11 Flow ในหน้า `/restaurant` ตั้งแต่ตั้งสูตร จัดซื้อและโอนของ ขายและส่งครัว
จนถึงคืนเงิน ปิดกะ และตรวจสิทธิ์ มีกรณี UAT 62 กรณี พร้อมตัวอย่างหนึ่งวันทำการที่ตรวจยอดต่อเนื่องได้
ข้อมูลทั้งหมดเป็นข้อมูลสมมติสำหรับร้านทดสอบ ไม่ใช่รายการขายหรือเอกสารที่เกิดขึ้นจริง

**ผลรอบ 27 ตุลาคม 2569:** pure tests ผ่าน 3,084 / ข้าม 6 / ล้มเหลว 0, production build ผ่าน,
browser fixtures ผ่าน 3 ชุด และตัวเลขตัวอย่างผ่านการตรวจด้วยสคริปต์แบบไม่เขียนข้อมูล
**ยังไม่ได้รัน UAT ทั้ง 62 กรณีกับฐานข้อมูลจริงในรอบนี้** จึงไม่ให้สถานะ PASS แก่กรณีเหล่านั้น
ผลคาดหวังในตารางใช้เป็นเกณฑ์ตรวจเมื่อทำ UAT ไม่ใช่หลักฐานว่า BMS บันทึกรายการนั้นแล้ว

## เตรียมร้านและข้อมูลตั้งต้น

ใช้ฐานข้อมูลทดสอบแยกจากร้านจริงและ tenant ชื่อ `FAKE BMS Cafe UAT` ตั้ง archetype เป็น `restaurant`
ก่อนเริ่มขาย เปิดความสามารถสูตร ตัวเลือก ครัว และของเสียตาม preset ร้านอาหาร
ระบบส่งข้อความ อีเมล และ payment provider ใช้ตัวจำลองหรือ local sink ไม่มีการส่งถึงลูกค้าจริง

ชุดฐานใช้เงินบาท ร้านไม่จด VAT ไม่มีค่าบริการ ไม่มีส่วนลดอัตโนมัติ ปิดแต้มและโปรโมชั่นไว้ก่อน
เปิดเฉพาะกรณีใน Flow 9 ส่วนเอกสาร VAT ใน Flow 10 ใช้ fixture แยกที่ตั้งค่าจด VAT แล้ว
การตั้งค่านี้มีไว้แยกตัวเลขทดสอบ ไม่ใช่คำแนะนำการจดทะเบียนภาษีของร้านจริง

- ลาเต้ 1 แก้ว: เมล็ด 20 กรัม + นม 150 มล. + แก้ว 1 ใบ = `10 + 6 + 2 = 18 บาท`
- อเมริกาโน 1 แก้ว: เมล็ด 20 กรัม + แก้ว 1 ใบ = `10 + 2 = 12 บาท`
- สูตรตัวอย่างนับแก้วทุกครั้งทั้งนั่งทาน/รับเองเพื่อให้ตัวเลขตรงกัน ร้านจริงต้องตั้งให้ตรงการใช้จริง
- ใช้จำนวนเต็มในหน่วยฐาน เช่น นม 5,000 มล. ไม่กรอก 5 แล้วให้ระบบเดาเองว่าเป็นลิตร
- ต้นทุนประมาณการใน catalog และมูลค่าสต็อกจริงเป็นคนละหลักฐาน ต้องตั้งทั้งสองส่วนให้ตรงกันใน fixture

| สาขา | เมล็ด กรัม | นม มล. | แก้ว ใบ | น้ำ ขวด |

ไม่แก้แถว inventory ตรง ๆ กรณีทดสอบข้อมูลต้นทุนขาด ให้แยก fixture ที่ยังไม่ยืนยันมูลค่าไว้ต่างหาก

### การเตรียมแต่ละรอบ

1. ติดตั้ง migration ที่ตรงกับรุ่นบนฐานทดสอบที่ restore แล้ว ตาม [แนวทางฐานทิ้งได้](../architecture/realtime-test-database.md)
2. ตั้งร้าน สาขา สิทธิ์ สินค้า สูตรที่เปิดใช้ สถานีครัว และโต๊ะ ตรวจว่าเมนูเปิดในช่องทางที่จะขาย
3. จับคู่เครื่องกับสาขา A ยืนยันพนักงาน และเปิดกะด้วยเงินตั้งต้น 500 บาท
4. ตรวจยอด available/reserved/on-hand และมูลค่าสต็อกก่อนเริ่ม เก็บภาพ/รายงาน baseline
5. แต่ละกรณี UAT เริ่มจาก baseline ของตัวเอง เว้นแต่ระบุให้ต่อจากขั้นก่อนหน้า
6. กรณีโปรโมชั่น แต้ม VAT และต้นทุนขาดต้องแยก fixture ไม่ให้เปลี่ยนยอดฐานของกรณีอื่น
7. จดเวลา ผู้ทำ ผู้อนุมัติ สาขา หมายเลขบิล/PO/ใบโอนที่ระบบสร้างจริง และ request key สำหรับการตรวจซ้ำ

## ขั้นตอนและผลคาดหวังครบ 11 Flow

สถานะ UAT จริงของทุกกรณีด้านล่างคือ **NOT_RUN ในรอบนี้**
การผ่าน pure test หรือหน้าจอที่จำลอง API ไม่ได้เปลี่ยนสถานะ UAT เป็น PASS
กรณีผิดพลาดต้องตรวจว่าไม่มีผลข้างเคียงค้าง เช่น เงินออก สต็อกเปลี่ยน สิทธิ์ถูกใช้ หรือ audit ที่อ้างว่าสำเร็จ

## วิธีรันซ้ำและบันทึกการตรวจรับ

จาก root ของ repository รันตัวเลขตัวอย่างโดยไม่ต้องมีฐานข้อมูล:

```bash
node apps/web/node_modules/tsx/dist/cli.mjs scripts/restaurant-uat-example.mts
```

ทดสอบ pure และ build:

```bash
node scripts/run-contract-tests.mjs pure
cd apps/web
npm run build
```

สำหรับ browser ให้เปิดเว็บ local ที่พอร์ต 3107 ก่อน แล้วจาก root รันทีละชุด:

```bash
BMS_SMOKE_URL=http://127.0.0.1:3107 node scripts/restaurant-public-browser-smoke.mjs
BMS_SMOKE_URL=http://127.0.0.1:3107 node scripts/branch-requisitions-browser-smoke.mjs
BMS_SMOKE_URL=http://127.0.0.1:3107 node scripts/stock-transfers-browser-smoke.mjs
```

ต้องติดตั้ง Playwright/Chrome หรือกำหนด `BMS_PLAYWRIGHT_MODULE` เป็น path ของโมดูลที่มีอยู่
ตัวตรวจเหล่านี้บล็อก external requests และแทน API ด้วย fixtures จึงใช้ยืนยันการทำงานของหน้าจอ
ไม่ใช่การส่ง transaction จริงผ่าน API ถึง DB

ก่อนทดสอบฐานจริง อ่าน [scripts README](../../scripts/README.md) และ harness ของชุดที่เลือก
ใช้ loopback กับฐานทิ้งได้ตามชื่อที่ suite อนุญาตเท่านั้น พร้อม migration/RLS/grants ที่ต้องใช้

### เงื่อนไขตรวจรับก่อนใช้กับร้านนำร่อง

- เคสที่มีเงินจริง/สต็อกจริงต้องตรวจทั้ง success, denial, retry และ rollback ในฐานทดสอบ
- ยอดจากบิล กะ คืนเงิน stock movement และ valuation ต้องเชื่อมกันได้ ไม่มีรายการซ้ำ
- ตรวจภาษาไทย/อังกฤษและหน้าจอ desktop/mobile; Windows/macOS/Linux ต้องตรวจ shell/keystore/เครื่องพิมพ์จริงแยก
- ทดสอบ printer/payment ที่ร้านจะใช้จริง และทดสอบเน็ตขาดในขั้นที่รองรับ; ไม่ถือว่า offline dine-in รองรับแล้ว
- ปัญหาที่ยังไม่ผ่านต้องระบุผู้รับผิดชอบและเงื่อนไขก่อนเปิดร้าน ไม่ใช้คำว่า PASS เพราะ Diagram แสดงครบ
- จบ UAT แล้วเก็บหลักฐานและคืน snapshot/ลบเฉพาะ tenant ทิ้งได้ตามวิธี teardown ที่อนุญาต ไม่ลบ ledger ของร้านจริง
