## ขอบเขตที่ใช้วางแผน

สมมติฐานเริ่มต้นคือคลินิกผู้ป่วยนอกในไทย ให้บริการที่สถานที่จริง เก็บค่าบริการจากผู้ป่วยโดยตรง และเริ่มทดลองหนึ่งสาขา การตรวจทางไกล การเคลมประกัน การเชื่อมแล็บ และงานเฉพาะทาง เช่น ทันตกรรมหรือความงาม เป็นขอบเขตที่ต้องกำหนดเพิ่มตามประเภทคลินิก **ไม่ควรใช้ CRM หรือแชททั่วไปเป็นเวชระเบียน** ระหว่างที่ยังไม่มีระบบคลินิก

ข้อเสนอมีสองทาง:

1. **เริ่มใช้กับงานธุรกิจ:** ให้ระบบเวชระเบียนคลินิกเดิมเป็นแหล่งข้อมูลจริงของผู้ป่วยและการรักษา ส่วน BMS รับเฉพาะข้อมูลที่จำเป็นสำหรับการลงทะเบียนหน้าร้าน การคิดค่าบริการ การรับเงิน และสต็อก หลังทดสอบการเชื่อมและสิทธิ์แล้ว ทางนี้มีขอบเขตการพัฒนาน้อยกว่า
2. **สร้างโมดูลคลินิกใน BMS:** เพิ่ม patient, appointment, encounter และ clinical record ที่แยกจาก CRM พร้อมผู้ประกอบวิชาชีพ สิทธิ์ ความปลอดภัย และวงจรชีวิตข้อมูลสุขภาพ ทางนี้ต้องผ่านการตรวจรับทางคลินิก กฎหมาย และการปฏิบัติงานก่อนใช้ข้อมูลจริง

ตัดสินใจทางเลือกแรกหรือที่สองก่อนออกแบบ schema และสัญญา API เพื่อไม่ให้ข้อมูลผู้ป่วยกระจายลง `bms_customers.note`, Inbox หรือ `bms_pharmacy_assessments` ระหว่างทำต้นแบบ

## หลักออกแบบ

```text
ผู้ป่วย (Patient/HN) ── นัดหมาย ── การเข้ารับบริการ (Encounter)
       │                               ├─ เวชระเบียน/เอกสารที่ลงนาม
       │                               ├─ คำสั่งตรวจ/ยา/ส่งต่อ
       │                               └─ ใบรายการค่าบริการ ── BMS Order/POS/Payment
       └─ ความสัมพันธ์กับผู้ปกครอง/ผู้ติดต่อ/ผู้จ่ายเงิน ── CRM
```

- `patient_id` เป็นตัวตนด้านการรักษา; `customer_id` เป็นตัวตนด้านการติดต่อ/การค้า ลิงก์สองส่วนต้องผ่านการตรวจสอบจากคน ไม่อนุมานจากชื่อ เบอร์ หรือ LINE ID; การ merge CRM ต้องไม่ย้ายหรือรวมเวชระเบียนโดยอัตโนมัติ
- แพทย์เป็นผู้รับผิดชอบการวินิจฉัยและลงนามบันทึก; สิทธิ์เภสัชกรและ `is_licensed_pharmacist` ใช้แทนสิทธิ์แพทย์ไม่ได้; Administrator ทั่วไปไม่ควรได้สิทธิ์อ่านข้อความรักษาเพียงเพราะเป็น super-role ใน RBAC เดิม
- การลงนาม/แก้เวชระเบียนต้องรักษาประวัติเวอร์ชัน ไม่เขียนทับฉบับที่ลงนามแล้ว; การแก้หลังลงนามเป็น addendum ที่ระบุผู้แก้ เวลา เหตุผล และความสัมพันธ์กับฉบับเดิม
- คำสั่งรักษาและการจ่ายยาเป็นคนละเหตุการณ์; การบันทึกใบสั่งยาไม่ตัดสต็อกหรือสร้างการชำระเงินเอง การจ่ายจริงจึงเชื่อมเข้าบริการสต็อก/การขายที่มีอยู่
- ข้อมูลสุขภาพไม่ไหลไปยัง CRM note, ข้อความการตลาด, search index ทั่วไป, AI tool เดิม, audit metadata, realtime event, log หรือรายงานยอดขายแบบระบุตัวบุคคล
- ธุรกรรมที่ถือครองข้อมูลผู้ป่วยต้อง derive tenant/branch จาก session และตรวจสิทธิ์บน server; ทุกตาราง tenant-owned ต้องมี RLS/grants และทุก mutation สำคัญต้อง audit ใน transaction เดียวกัน

### ทางเชื่อม EMR เดิม: ขอบเขตงานที่เล็กกว่า

ถ้าคลินิกมี EMR อยู่แล้ว ให้ EMR เป็นเจ้าของ HN, นัดหมาย, visit, เวชระเบียน และการลงนามทั้งหมด BMS รับเพียง `externalEncounterRef` ที่ผูก tenant/branch และรายการค่าบริการที่เจ้าหน้าที่ตรวจแล้ว โดยไม่รับอาการ วินิจฉัย หรือภาพผลตรวจเข้าระบบค้าขาย สร้าง adapter พร้อมการพิสูจน์ตัวตนระหว่างระบบ, schema/version ของ payload, idempotency, outbox/retry และรายการกระทบยอดกรณีรับเงินสำเร็จแต่ส่งสถานะกลับ EMR ไม่สำเร็จ การยกเลิก/คืนเงินต้องให้ทั้งสองระบบแสดงสถานะตรงกันโดยไม่ลบเวชระเบียน

เส้นทางนี้ไม่ต้องสร้าง patient chart หรือ appointment ใน BMS; ระยะ 1 ทำเฉพาะ clinical-data boundary และ identity mapping ที่จำเป็นต่อการเงิน ระยะ 2–3 ข้ามได้หาก EMR เดิมเป็นเจ้าของงานนั้นจริง ทดลองด้วยข้อมูลสังเคราะห์ก่อนเชื่อม production

## ลำดับพัฒนาและเกณฑ์รับมอบ

### ระยะ 0 — ตกลงขอบเขตและเลือกทางสถาปัตยกรรม (P0)

**งาน:** เก็บ workflow จริงตั้งแต่รับนัด → ลงทะเบียน → ตรวจ → สั่งยา/แล็บ → คิดเงิน → นัดติดตาม, ระบุประเภทคลินิกและผู้ประกอบวิชาชีพ, จำนวนสาขา, ผู้เยาว์, การเคลม, ระบบเวชระเบียนเดิม, และข้อมูลที่ต้องส่งระหว่างระบบ ทำ data map และ threat model สำหรับทุกช่องทาง รวมถึง support และ platform admin

**ผลส่งมอบ:** ขอบเขต pilot ที่แพทย์ผู้รับผิดชอบ, ผู้ดูแลคลินิก, ผู้รับผิดชอบข้อมูลส่วนบุคคล และบัญชี/ภาษีเห็นตรงกัน; เลือก **เชื่อม EMR เดิม** หรือ **สร้าง EMR ใน BMS**; รายการข้อมูลและเจ้าของข้อมูลจริงของแต่ละขั้นตอน; เกณฑ์หยุด/ย้อนกลับ pilot

**ผ่านเมื่อ:** ไม่มีขั้นตอนที่ต้องพิมพ์ข้อมูลรักษาใน CRM/Inbox เพื่อชดเชยโมดูลที่ขาด และมีผู้รับผิดชอบการตัดสินใจทางคลินิก/การเปิดเผยข้อมูลชัดเจน

### ระยะ 1 — กำแพงข้อมูลและสิทธิ์ผู้ป่วย (P0; ทำก่อนข้อมูลจริง)

**งาน:** เพิ่ม clinic feature gate ที่ปิดเป็นค่าเริ่มต้น; ถ้าสร้าง EMR ให้เพิ่ม `bms_clinic_patients` (HN ที่ไม่ชนกันตามขอบเขตคลินิก), `bms_clinic_patient_contacts`/representatives, verified link ไปยัง customer, และ clinic practitioners พร้อมประเภทวิชาชีพ/หลักฐานใบอนุญาต/สถานะใช้งาน; เพิ่ม permission catalog สำหรับ registration, scheduling, clinical read/write/sign, billing และ break-glass โดยมี clinical access check เพิ่มจาก RBAC เดิม; บันทึกทั้งการแก้ไขและการเปิดอ่านข้อมูลอ่อนไหว เส้นทางเชื่อม EMR ใช้เพียง mapping ที่จำเป็นต่อการคิดเงินและห้ามให้ customer ID เป็นอำนาจเปิด chart

**ความเป็นส่วนตัว:** กำหนด lawful basis สำหรับการรักษาแยกจากการตลาด, privacy notice, หนังสือ/หลักฐานยินยอมสำหรับหัตถการหรือการส่งข้อมูลเมื่อจำเป็น, สิทธิ์เจ้าของข้อมูล, ระยะเก็บรักษาและ legal hold ที่ทบทวนโดยผู้เชี่ยวชาญ, ข้อตกลงกับผู้ประมวลผลข้อมูล/ผู้ให้บริการโฮสต์ และแผนเหตุข้อมูลรั่วไหล; ตั้งค่าไฟล์ส่วนตัว, การเข้ารหัส, backup และ restore

**ผ่านเมื่อ:** ทดสอบแยก tenant, branch, role, care team และผู้ปกครอง; ผู้ไม่มีสิทธิ์เปิดไฟล์หรือ GraphQL โดยเดา ID ไม่ได้; การเข้าถึงฉุกเฉินต้องให้เหตุผลและเข้ารายงานตรวจสอบ; restore จาก backup ในเครื่องทดสอบได้; ไม่มีข้อมูลสุขภาพใน log, audit metadata, report หรือ AI ที่ไม่ได้อนุมัติ

### ระยะ 2 — นัดหมายและลงทะเบียน (P0 เมื่อ BMS เป็นเจ้าของตารางนัด)

**งาน:** เพิ่ม practitioner availability, slot/room/resource, `bms_clinic_appointments`, cancellation/reschedule policy, waitlist ตามความต้องการ, check-in และสถานะ no-show; สร้างหน้า receptionist calendar, patient search/registration และข้อมูลติดต่อผู้ปกครอง; แจ้งเตือนนัดแบบข้อความทั่วไปที่ไม่เผยโรคหรือหัตถการ; รองรับการเรียกซ้ำด้วย idempotency key และ transaction/lock กัน double booking

**ผ่านเมื่อ:** ผู้ใช้สองคนจองช่องเดียวกันพร้อมกันแล้วมีได้เพียงนัดเดียว; การเลื่อนนัดไม่ทำข้อมูล visit/เงินหาย; พนักงานเห็นเฉพาะข้อมูลที่จำเป็น; ลูกค้าไม่สามารถเปิดนัดของคนอื่นด้วยลิงก์/รหัสที่เดาได้

### ระยะ 3 — เวชระเบียนผู้ป่วยนอก (P0 หากเลือกสร้าง EMR)

**งาน:** เพิ่ม `bms_clinic_encounters` และข้อมูลแยกหมวดสำหรับอาการ, ประวัติแพ้ยา, สัญญาณชีพ, ผลตรวจ, การวินิจฉัย, การรักษา/หัตถการ, คำสั่งยา/แล็บ, การส่งต่อ และเอกสารแนบ; สร้างหน้าลงบันทึกตามบทบาทแพทย์/พยาบาล, draft → signed → amended, ระบุผู้ตรวจและเวลาลงนาม; เก็บบันทึกที่ลงนามแบบแก้ไขตรงไม่ได้ พร้อม addendum; สร้าง export/print ราย visit และประวัติทั้งรายตามสิทธิ์

**ผ่านเมื่อ:** ระเบียนมีรายการข้อมูลที่คลินิก/ผู้กำกับกำหนด, ทุกบันทึกผูก patient + visit + ผู้ทำ + เวลา, เปิดอ่าน/แก้ไขย้อนหลังตรวจได้, แก้หลังลงนามแล้วฉบับเดิมยังอยู่, ไม่มีข้อมูลข้ามผู้ป่วยแม้มีชื่อหรือเบอร์ซ้ำ; แพทย์ตรวจรับแบบฟอร์มและกรณีทดสอบด้วยข้อมูลสังเคราะห์

### ระยะ 4 — ค่าใช้จ่าย ยา และการเงิน (P0 สำหรับการใช้ BMS รับเงิน)

**งาน:** ออกแบบ charge sheet ผูก encounter กับรายการบริการ/ยา/เวชภัณฑ์; ให้ผู้มีสิทธิ์ตรวจราคาและรายการก่อนส่ง BMS `createOrder()`/POS; ใช้ idempotency key และสถานะกระทบยอดเมื่อ clinical action กับ payment อยู่คนละ transaction; การจ่ายยาจริงจึงใช้ stock movement/lot/expiry ที่มีอยู่; ตรวจแนวทางราคา ภาษี เอกสารรับเงิน คืนเงิน และเงินมัดจำของบริการคลินิกกับผู้เชี่ยวชาญก่อนใช้โมเดล `NON_STOCK` หรือ `bms_order_extra_lines`

**ผ่านเมื่อ:** visit เดียวไม่เรียกเก็บซ้ำจาก retry; ยอด invoice/payment ตรงกับรายการที่ยืนยันและ `bms_order_items.line_amount`; สั่งยาอย่างเดียวไม่ตัดสต็อก; void/refund ไม่ลบเวชระเบียน; รายงานการเงินไม่เผยการวินิจฉัยโดยไม่จำเป็น

### ระยะ 5 — การสื่อสารและ AI (P1; หลัง clinical workflow ใช้ได้)

**งาน:** เริ่มจากข้อความนัดหมายและคำถามทั่วไปแบบไม่มีข้อมูลรักษา; หากต้องการ intake ก่อนพบแพทย์ ให้ใช้แบบฟอร์มและเส้นทางข้อมูลแยกจาก Inbox/AI การค้า พร้อม consent/lawful basis, clinician review, และ fallback ส่งต่อคน; AI อาจช่วยจัดรูปแบบหรือร่างสรุปภายในภายหลัง แต่ต้องผ่าน provider/data-handling review และไม่มีสิทธิ์วินิจฉัย สั่งยา ลงนาม หรือยืนยันคำตอบทางคลินิกเอง

**ผ่านเมื่อ:** ไม่มี chart data เข้าสู่ provider, tool, prompt, transcript หรือ QA store โดยไม่ได้อนุมัติ; ข้อมูลที่ AI ร่างแยกจากบันทึกที่แพทย์ลงนาม; ระบบยังทำงานได้เมื่อ provider ล่ม; ชุดทดสอบครอบคลุมข้อความฉุกเฉิน ข้อมูลไม่ครบ ความกำกวม และการเปิดเผยผิดคน

### ระยะ 6 — ทดลองและเปิดใช้ (P0 release gate)

**งาน:** ใช้ข้อมูลสังเคราะห์บน throwaway DB ก่อน, migration idempotency/RLS/grants, denial/rollback/duplicate tests, browser desktop/mobile, ทดสอบ backup restore, load สำหรับปฏิทินและเวชระเบียน, tabletop incident, ทดลองงานจริงหนึ่งสาขาโดยผู้ประกอบวิชาชีพและฝ่ายเวชระเบียน; สอนเจ้าหน้าที่และทำคู่มือ in-app; เปิด flag เฉพาะ tenant pilot หลังอนุมัติ

**Go/No-Go:** ผู้รับผิดชอบทางคลินิกลงนามตรวจ workflow/แบบฟอร์ม; ผู้รับผิดชอบข้อมูลอนุมัติ data map, access, retention และ provider contract; บัญชีอนุมัติ charging/tax; ผ่าน test ที่ขอบเขตจริงและ restore; มีช่องทางแก้เหตุและแผน rollback; ไม่มีข้อมูลจริงใน dev/test/log/AI eval; ไม่อ้างว่าพร้อมใช้คลินิกทั่วไปจากผล pilot หนึ่งแห่ง

## ประเด็นกฎหมายและข้อกำหนดที่ต้องให้ผู้เชี่ยวชาญตัดสิน

- [แนวตรวจคลินิกของกรมสนับสนุนบริการสุขภาพ](https://hss.moph.go.th/fileupload_doc/2025-09-03-35-25-151540-364.pdf) ระบุทะเบียนผู้ป่วย เลขประจำตัว วันที่รับบริการ และเวชระเบียนที่บันทึกอาการ/ผลตรวจ/วินิจฉัย/การรักษา/ผู้รักษา ใช้เป็น checklist ออกแบบขั้นต่ำ แล้วให้ผู้รับผิดชอบคลินิกยืนยันข้อกำหนดที่ใช้กับใบอนุญาตและประเภทคลินิกของตน
- [PDPA มาตรา 26 และ 37](https://mdes.go.th/law/detail/3541pdf) จัดข้อมูลสุขภาพเป็นข้อมูลอ่อนไหวและกำหนดหน้าที่เรื่องความปลอดภัย/การลบเมื่อเข้าเงื่อนไข ฐานการประมวลผลอาจเป็นความยินยอมโดยชัดแจ้งหรือข้อยกเว้นที่กฎหมายกำหนดตามกรณี ให้ผู้เชี่ยวชาญกฎหมายระบุฐานและระยะเก็บรักษาจริงก่อนสร้าง policy; ไม่กำหนดจำนวนปีเองในโค้ด
- [กรมสนับสนุนบริการสุขภาพ](https://prgroup.hss.moph.go.th/info/news/2033) ย้ำการแสดงอัตราค่ารักษา ยา เวชภัณฑ์ และค่าบริการให้ชัดเจน จึงต้องทบทวน pricing/receipt/tax flow แยกจาก POS ร้านค้าทั่วไป
- หากเพิ่มตรวจทางไกล ให้เปิดเป็นโครงการแยกและตรวจ [แนวทางแพทยสภาเรื่องโทรเวชและคลินิกออนไลน์](https://tmc.or.th/Media/media-2020-07-24-10-40-22.PDF) รวมถึงกฎปัจจุบันก่อนออกแบบ video/remote prescribing; แผน pilot นี้ยังไม่ครอบคลุม
