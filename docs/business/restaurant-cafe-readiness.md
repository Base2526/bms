## ข้อสรุป

ระบบมีแกนหลักสำหรับร้านอาหารและคาเฟ่แล้ว: หน้าร้าน โต๊ะ รอบสั่ง ครัว
ออเดอร์ออนไลน์ สต็อกวัตถุดิบ และรายงานต้นทุน ไม่ควรใช้คำว่า “ครบทุกระบบ”
หรือ “เชื่อมทุก delivery platform” เพราะยังมีข้อจำกัดด้านการเชื่อมต่อและอุปกรณ์

**เลือกรูปแบบร้านให้ถูกตอน onboarding:** คาเฟ่ที่ต้องใช้โต๊ะ QR และ KDS ต้องตั้งเป็น
`restaurant` ส่วน `food_beverage` ใช้ flow สินค้า/ออเดอร์แบบค้าปลีก
ไม่ได้รับ restaurant branch/hours/kitchen rules โดยอัตโนมัติ
ประเภทตั้งต้นถูกล็อกหลังมีออเดอร์จริง จึงควรตรวจให้ถูกก่อนเริ่มขาย

## ช่องว่างที่แก้ในรอบนี้: รับเองที่ร้าน

1. Checkout เคยบังคับที่อยู่จัดส่งแม้ออเดอร์เป็น PICKUP ทำให้ลูกค้าที่มีชื่อ/โทรครบส่งสลิปไม่ได้
   ตอนนี้ยกเว้นเฉพาะ PICKUP ที่อ่านจากออเดอร์ในฐานข้อมูล ไม่รับคำอ้างจาก request
   ซ่อนที่อยู่ของลูกค้าบน checkout รับเอง และแสดงชื่อสาขาที่อ่านจากระบบ
2. การแก้ข้อมูลลูกค้าเคยคำนวณค่าส่งใหม่ให้ออเดอร์ PICKUP/POS ได้ ตอนนี้ตัดออกจากรายการ
   DELIVERY ยังคำนวณได้ แต่ต้อง recheck สถานะ รายการ ยอด ที่อยู่ carrier และ payment
   หลังได้ order lock; บันทึกค่าและ audit ใน tenant transaction เดียวกัน
   เรียก carrier ก่อนเปิด transaction จึงไม่รอ network ขณะถือ order lock
3. ส่งมอบ PICKUP เคยติดเงื่อนไขไม่มีที่อยู่ ตอนนี้ใช้ stock handover เดิมโดยยกเว้นที่อยู่
   และล็อก order ป้องกันคำขอซ้ำตัด stock ซ้ำ DELIVERY ยังตรวจที่อยู่เหมือนเดิม
4. หน้าลูกค้าและปุ่มหลังบ้านใช้คำว่า “รับเอง/ส่งมอบที่ร้าน” ทั้งไทยและอังกฤษ
   ก่อนยืนยันต้องตรวจผู้รับและส่งมอบจริง ชำระแล้วไม่แสดงข้อความว่าอาหารพร้อม
   สถานะฐานข้อมูลยังใช้ PACKING/SHIPPED ตามเดิม ไม่สร้าง shipment ของผู้ขนส่งสำหรับ handover

ไม่มี migration หรือการแก้ข้อมูลออเดอร์เดิมอัตโนมัติ
หากออเดอร์เก่าเคยถูกคิดค่าส่งผิด ต้องตรวจยอดและสถานะการชำระก่อนแก้เป็นรายออเดอร์

## ข้อจำกัดก่อนใช้ข้อความโฆษณา

- foodpanda ยังเป็น sandbox/shadow; GrabFood และ LINE MAN ยังติด contract
  ห้ามสื่อว่าเชื่อม production พร้อมใช้แล้ว
- ยังไม่มีการเลือกเครื่องพิมพ์แยก station แบบครบ flow หรือ offline dine-in sync
  Emergency Offline เป็น plain-retail cash queue ตามข้อจำกัดเดิม
- ยังไม่มีระบบบัตรคิวลูกค้าและเรียกคิวผ่าน SMS/LINE ที่ครบวงจร
- อีเมลสถานะใช้ template กลาง `order.packing/order.shipped` ยังไม่มี template รับเองแยก
  ร้านที่เปิดอีเมลแจ้งสถานะต้องตรวจ wording ของ template ก่อนใช้กับ pickup
- จองโต๊ะในแชตไม่ควรใช้คำว่า “จองสำเร็จทันที” หรือ “การันตีโต๊ะ”
- ต้องทดลองกับ printer/payment/provider ที่จะใช้จริง และทดสอบรับออเดอร์จนส่งมอบ
  ของร้านนำร่องก่อนเปิดแคมเปญขาย ข้อความด้านภาษีไม่ควรสื่อว่าเป็น e-Tax อัตโนมัติ

ข้อความตั้งต้นที่ตรงกับฟีเจอร์:

> จัดการร้านอาหารและคาเฟ่ ตั้งแต่รับออเดอร์หน้าร้านและแชต โต๊ะและงานครัว
> ไปจนถึงวัตถุดิบและรายงานต้นทุน พร้อมให้ทีมร้านตรวจและยืนยันขั้นตอนสำคัญ

ตัวอย่าง demo: เปิดโต๊ะ → เพิ่มเมนู/ตัวเลือก → ส่งครัว → ชำระ → ดู stock/cost;
อีกเส้นทางคือแชต PICKUP → เลือกสาขา/รายการและยืนยันคำขอ → เก็บชื่อ/โทร →

หน้าใหม่เชื่อมจากหน้าแรกและ footer เพื่อให้ผู้สนใจสำรวจ 11 Flow ใน 4 หมวด:
เตรียมร้านและวัตถุดิบ, ขายและบริการลูกค้า, ต้นทุนและการเงิน, สิทธิ์และความถูกต้อง
แต่ละ Flow แสดง Sequence Diagram เต็ม รวมกรณียกเว้นและเงื่อนไข พร้อมซูม,
เลื่อนแนวนอนบนมือถือ, ข้อความขั้นตอน และลิงก์ตรง `#flow-1` ถึง `#flow-11`.
ส่วนหัวใช้สองคอลัมน์บนจอใหญ่ และโหมด “พอดีความกว้าง” (Fit width) ของ Diagram ขยายเต็มความกว้างกรอบ;
มือถือคงขนาดตัวอักษรที่อ่านได้และเลื่อนแนวนอนได้ แทนการย่อทุกคอลัมน์ลงจอเล็ก.

ปุ่ม **พิมพ์ / PDF Flow นี้** เปิดหน้าต่างพิมพ์ของเบราว์เซอร์ ให้เลือก Save as PDF

เงื่อนไขที่ต่อจากหน้าก่อน เลขหน้า ขอบเขต และลิงก์ต้นทาง ไม่พิมพ์เมนูเว็บหรือขึ้นกับซูมบนจอ.
ปุ่ม **แชร์ Flow นี้** ใช้เมนูแชร์ของเครื่องเมื่อรองรับ และใช้ clipboard เป็น fallback;
การยกเลิกเมนูแชร์ไม่คัดลอกอะไร ปุ่มคัดลอกลิงก์ยังมีแยกต่างหาก.

### ตัวเลือกประเภทร้านและการเล่นทีละขั้น

หน้า `/restaurant` ให้ผู้ชมเลือกตัวอย่าง `restaurant`, `food_beverage`,
`board_game_cafe` หรือดูภาพรวม โดยการเลือกมีผลเฉพาะคู่มือสาธารณะ ไม่แก้
`business_archetype` หรือ capability ของร้านจริง. ร้านอาหารเลือก Dine-in,
Takeaway หรือออนไลน์ได้ และตัวเลือกหลายสาขาใช้จัดลำดับ Flow ที่แนะนำ.
ลิงก์บันทึก `shop`, `service`, `branches` และ `#flow-N` โดยลิงก์ `#flow-N`
เดิมยังเปิดได้. Flow ที่ไม่ตรงกับร้านยังเปิดอ่านได้พร้อมป้ายว่าเป็นตัวอย่างร้านอาหาร.

Flow 3 มีบทเฉพาะสำหรับร้านอาหาร Takeaway, คาเฟ่หน้าเคาน์เตอร์ และ
บอร์ดเกมคาเฟ่. คาเฟ่ไม่ถูกอธิบายว่าได้ restaurant-only online ordering,
Takeaway ไม่มีโต๊ะหรือ QR โต๊ะ, และบอร์ดเกมใช้ billing group สำหรับยอดเงิน
โดยแยกเวลาเล่นกับสินค้าที่ขาย. Flow อื่นคงหมายเลข 1–11 และแสดงความเหมาะสม
ตามประเภท; Flow ที่ยังเป็นเรื่องของร้านอาหารแสดงป้ายขอบเขตชัดเจน.

ตัวเล่นสร้างเส้นทางจาก `alt`/`opt` ใน sequence ที่ตรวจ syntax แล้ว
ผู้ชมเลือกกรณีได้และตัวเล่นแสดงเฉพาะกรณีที่เลือก พร้อมเน้นเหตุการณ์ใน SVG,
คำบรรยายบนหน้าจอ และเสียงสังเคราะห์ของเบราว์เซอร์เมื่ออุปกรณ์มีเสียงตรงภาษา.
หากไม่มีเสียง ระบบเล่นภาพและคำบรรยายตามเวลาโดยแจ้งสถานะให้เห็น.
เสียงเริ่มหลังผู้ใช้กด Play เท่านั้น หยุดเมื่อออกจากหน้าหรือเปลี่ยน Flow.
แผนภาพเต็ม transcript และหน้าพิมพ์ยังแสดงทุกเงื่อนไขเพื่อให้อ่านบริบทครบ.
เสียงนี้เป็นเสียงจากอุปกรณ์ ไม่ใช่ไฟล์เสียงบันทึกที่ผ่านการตรวจการออกเสียง
บนทุกแพลตฟอร์ม.

การตรวจซ้ำแก้เส้นทางที่ไม่สำเร็จให้หยุดก่อนรับเงิน/ส่งมอบ (Flow 3 และ 7),
ยกเลิกยอดค้างรับได้เฉพาะ PO ที่ยังรับไม่ครบ (Flow 8), และแยกยกเลิกก่อนขาย
ออกจากการชำระ/คืนหลังขาย พร้อมขอส่วนลดก่อนยืนยันยอด (Flow 9).
ตัวเล่นเริ่มจากกรณีแรกที่ผู้เขียนกำหนด ขั้นตอน `opt` ปิดไว้จนผู้ชมเลือก
และ `loop` ระบุว่าแสดงตัวอย่างหนึ่งรอบ. การ์ดปัจจุบันแสดงผู้ส่ง–ผู้รับและลูกศร
เคลื่อนไหวเฉพาะตอนเล่น โดยเคารพ reduced motion.

เมื่อเสียงล้มเหลวหรือไม่เริ่มภายใน 5 วินาที ตัวเล่นแจ้งสถานะและใช้คำบรรยายตามเวลา
ต่อไป; เสียงที่เริ่มแล้วมี timeout ตามความยาวข้อความป้องกันการค้างไม่จบ.
เปิดเสียงอีกครั้งเพื่อ retry ได้. Pause หยุดเสียงและเมื่อเล่นต่อจะเริ่มอ่านขั้นปัจจุบันใหม่.
เปลี่ยน Flow/ภาษา/รูปแบบร้าน/จำนวนสาขาจะหยุดและเริ่มตัวเล่นใหม่.
ผลการแชร์ที่กลับมาหลังเปลี่ยนตัวเลือกจะไม่ย้อน URL หรือสถานะปัจจุบัน.
`scripts/restaurant-playback-browser-smoke.mjs` ตรวจกรณีเหล่านี้ด้วยเสียงจำลอง
จึงไม่แทนการฟังคุณภาพเสียงจริงของแต่ละอุปกรณ์.

### ขอบเขต Desktop / Mobile ของคู่มือสาธารณะ (27 ต.ค. 2569)

`/restaurant` เป็นหน้าเว็บอธิบายระบบ ไม่ใช่ route ของเครื่อง POS และไม่ได้เพิ่มหรือเปลี่ยน
GraphQL/REST, schema, permission หรือการคำนวณเงิน/สต็อก จึงไม่ต้องอัปเดต installer/APK/IPA
เพื่อให้การเปลี่ยน Diagram มีผล การเปิดคู่มือและพิมพ์/แชร์ใช้เบราว์เซอร์ของอุปกรณ์.

| งานใน Diagram | ช่องทางที่ตรวจพบในโค้ด |
| --- | --- |
| สูตร ราคา ต้นทุน และรายงาน (1, 4) | เว็บหลังบ้าน; POS อ่านข้อมูลที่ตั้งแล้วและส่งรายการขาย |
| คำขอเติมสินค้า / รวมคำขอ / สร้าง PO (2, 8) | เว็บหลังบ้าน; Mobile มีรับ PO และงานโอน/ตรวจนับสาขา |
| โต๊ะ รอบครัว ย้าย/แยก/รวมบิล และรับเงิน (3, 6) | Web POS ที่ Desktop ใช้ และหน้าจอ Native Mobile |

หลักฐานเส้นทาง: Desktop `src/renderer-route.mjs` เลือก `/pos/app` (fallback `/pos`

`src/main.mjs` เปิดหน้าที่ไม่ใช่ POS ใน system browser โดยไม่ให้สิทธิ์ IPC ของ POS.
Native ใช้ `MainTabs.tsx`, `CheckDetailScreen.tsx`, `OperationsScreen.tsx`,
`InventoryScreen.tsx` และ `graphql/operations.graphql` ไม่ได้ import public guide.
การพิมพ์คู่มือใช้ CSS ที่มี `[data-restaurant-print]` จึงไม่เปลี่ยนใบเสร็จ POS.

ตรวจผลกระทบ: Desktop lint + 68/68 tests ผ่าน; Mobile typecheck + Jest 37 suites,
252/252 tests ผ่าน. เป็นการตรวจโค้ดและชุดทดสอบบน host macOS ไม่ใช่การเปิดแอปจริงครบ
Windows/Linux/macOS/Android/iOS หรือการทดสอบเครื่องพิมพ์จริง และไม่ได้รับรอง parity ทุกฟีเจอร์.

## การรวมงานค้าปลีกและร้านอาหาร

รวมงานร้านอาหารเข้ากับ `codex/retail-online-readiness` แล้ว โดยเก็บทั้ง IP/token rate limits,
ขนาด JSON ที่จำกัด, การปฏิเสธ payment เมื่อสถานะออเดอร์เปลี่ยน และ flow PICKUP ในชุดเดียวกัน
เพิ่ม regression ที่นำผลจาก checkout service จริงผ่าน payment route ที่มี rate limit
เพื่อตรวจว่ารับเองที่มีข้อมูลครบผ่านขั้นตรวจ contact ได้ และ DELIVERY ยังต้องมีที่อยู่
