# รับออร์เดอร์อาหารทางแชท + เดลิเวอรี — บรีฟสำหรับ agent

> เอกสารนี้เขียนเพื่อให้ **agent อ่านแล้วลงมือได้ทันที** โดยไม่ต้องมีบทสนทนาก่อนหน้า
> ทุกข้อเท็จจริงในหัวข้อ "สภาพโค้ดปัจจุบัน" ถูกตรวจกับซอร์สจริงแล้ว (2026-09-04) พร้อมเลขบรรทัด
> **ก่อนเชื่อบรรทัดใดบรรทัดหนึ่ง ให้เปิดไฟล์ยืนยันก่อนเสมอ** — โค้ดอาจขยับหลังจากวันที่เขียน

## 0. โจทย์

ร้านอาหาร (`business_archetype = 'restaurant'`) ต้องรับออร์เดอร์อาหารทางแชท (LINE/Inbox) และส่ง
เดลิเวอรีได้ เพื่อเพิ่มยอดขาย

**วันนี้ทำไม่ได้เลย** — เมนูร้านอาหารประกาศช่องทางขายไว้แค่ `RESTAURANT_POS` ทุกเส้นทาง ฝั่ง AI
จึงมองไม่เห็นเมนูสักตัว ลูกค้าถาม "ขอกะเพราหมู 2" แล้วได้คำตอบว่า *"ไม่พบสินค้า ลองระบุชื่อ **รุ่น สี**
หรือหมวดสินค้า"*

## 2. กฎที่ห้ามละเมิด (invariants ของโปรเจกต์นี้)

1. **ราคาและเงินมีสูตรเดียว** — ห้ามเขียนสูตรที่สองที่ตัดสินว่า "คืนเงินเท่าไร" หรือ "ราคาต่อหน่วยเท่าไร"
   repo นี้เคย drift มาแล้วหลายรอบ (`unitPriceForQty`, VAT, ค่าคอมมิชชัน)
2. **audit ต้องอยู่ในทรานแซกชันเดียวกับเงิน/สต็อกที่มันบันทึก** — ห้าม best-effort หลัง commit
3. **ทุกจุดที่ขยับสต็อกอ่านจาก view `bms_order_stock_lines`** ห้ามอ่าน `bms_order_items` ตรง
   (เคยหลุด 2 จุด และมีเทส `scripts/order-stock-lines-contract.test.mts` คุมอยู่)
4. **REST route ทุกตัวมีการ์ดของตัวเอง** — `middleware.ts` กันแค่ `/admin/**`
   `/api/bms/*` ใช้ `authorizeAdminRoute(permission)` · `/api/pos/*` ใช้ device token + PIN ·
   **tenant มาจาก session/อุปกรณ์เสมอ ห้ามรับจาก body**
5. **AI ห้ามแต่งตัวเลข** — ทูลต้องคืน "สถานะ" ไม่ใช่จำนวน สำหรับสินค้าที่ไม่นับสต็อก
   (คืนเลข 0 หรือ 9999 = ยื่นตัวเลขปลอมให้โมเดลเอาไปพูด)
6. **เพิ่มค่าใหม่ในคอลัมน์ที่มี CHECK = ต้องมี migration คู่เสมอ** — `9.42` ลืมทำ ทำให้การตัดของเสีย
   ล้ม 100% โดยไม่มีใครรู้ · `8.9` ต้องเพิ่ม `STORE_CREDIT` เข้า CHECK **สองที่**
7. **migration ต้อง apply ก่อน deploy โค้ดเสมอ** — ตารางใหม่ในงานนี้ถูกอ่านทุกบิลของทุกร้าน
   (กฎเดียวกับ `9.40`/`9.51`/`9.52`) ฐานที่ยังไม่ apply = **ขายไม่ได้ทั้งระบบ ไม่ใช่แค่ร้านอาหาร**
8. **`DROP VIEW` ทิ้ง GRANT ไปด้วย** — ทุกครั้งที่แตะ `bms_order_stock_lines` ต้อง
   `GRANT SELECT ... TO bms_app` ใหม่ ไม่งั้นทุกเส้นทางที่เขียนของล้มด้วย `42501`
9. **ตั้งเลข migration ด้วยการดูของจริงก่อนเสมอ** — `ls db/migrations | sort -V | tail`
   (เลขล่าสุด ณ วันเขียนคือ **9.54**) · เลขซ้ำข้าม branch เกิดบ่อยมากใน repo นี้
10. **ห้ามใช้ `pnpm`** — repo ลงด้วย npm

### 3.4 สิ่งที่ยังไม่มีเลยในระบบ (ต้องสร้าง)

- ธง "ปิดขายชั่วคราว / หมดวันนี้" — ค้นทั้ง repo แล้วไม่มี `sold_out` ที่ไหน ·
  วิธีเดียววันนี้คือ `active = false` ซึ่ง **ถอดสินค้าออกจากทุกช่องทางพร้อมกัน** และเปิดกลับต้องผ่าน readiness ใหม่
- **หน้าจอคิวคืนเงิน** — ผู้เรียก `completePosRefundAllocation` มีที่เดียวคือ
  `apps/web/app/api/pos/refund-settlement/route.ts` · **ไม่มีหน้าจอ ไม่มี GraphQL query** ที่ list รายการค้าง
  → แปลว่าวันนี้การคืนเงินแบบไม่ใช่เงินสดก็อาจค้าง `PENDING` โดยไม่มีใครเห็นอยู่แล้ว
- ตัดรายการออกจากบิล — `cancelOrderInTx` / `returnOrder` เป็น **ทั้งบิล** เท่านั้น
  (`apps/web/lib/bms/orders.ts:1583`, `:1520`) และไม่มีเส้นทางไหนแก้แถว `bms_order_items` ของบิลออนไลน์
- ปิดตั๋วครัว **รายรายการ** — `cancelKitchenTicketsForOrderInTx` เป็นทั้งบิล (`kitchen.ts:151`)
- คืนเงิน **บางส่วน** ของบิลออนไลน์ — `refundPayment` เป็น `CONFIRMED → REFUNDED` ทั้งก้อน ไม่มีจำนวน
  (`apps/web/lib/bms/payments.ts:533`)
- คืนแต้มบางส่วนของบิลออนไลน์ — `reversePointsForReturnInTx` **บังคับ `posReturnId`**
  (`apps/web/lib/bms/membership.ts:853`)
- ประเภทการรับของ (ส่ง/รับเอง) + เวลาที่สัญญา — ไม่มีคอลัมน์
- เวลาทำการที่บังคับได้ — `business_hours` เป็น **free text** (`6.9`)
- ต้นเหตุการยกเลิก (ร้าน/ลูกค้า)
- เพดาน "ร้านรับส่วนต่าง" ระดับร้าน

### 3.5 บั๊กที่ใช้งานอยู่จริงวันนี้ ต้องแก้ไปด้วย

**บั๊ก A — modifier ที่ไม่ผูกวัตถุดิบ ทำให้บิลถูกปฏิเสธทั้งใบ**

- สาขา `RECIPE` ดึง modifier ด้วย **INNER JOIN** ไปที่ `bms_product_modifier_items`
  (`apps/web/lib/bms/stockConsumption.ts:198`) → รหัสที่ไม่มีแถววัตถุดิบ = `MODIFIER_NOT_FOUND`
- ตัวสร้างข้อมูลตัวอย่าง **ไม่เคยเขียน `bms_product_modifier_items` เลยสักแถว**
  (`apps/web/lib/bms/devSeed.ts:803` เขียนแต่ `price_delta`)
- เส้นทางจริง: หน้าโต๊ะเก็บรหัส → `toOrderItem` (`restaurantPos.ts:613`) → `createOrderInTx`
  → throw → **ส่งครัวไม่ได้ทั้งรอบ**
- กระทบตัวเลือกที่ร้านอาหารใช้บ่อยที่สุด: ไม่ใส่ผัก · ไม่ใส่ผักชี · แยกข้าว · หวานน้อย ·
  ไม่ใส่น้ำแข็ง · ใส่แก้วกลับบ้าน (+5)
- จอยังโชว์ตัวเลือกให้กดปกติ เพราะฝั่งอ่านใช้ **LEFT JOIN** (`productRecipes.ts:202`)
  = "จอบอกอย่าง server ตอบอีกอย่าง"
- **ทางแก้**: แยก modifier เป็นสองชนิด — *แบบมีผลกับวัตถุดิบ* (ต้องมีสูตร) กับ
  *แบบเป็นคำสั่ง/ราคาอย่างเดียว* (ไม่ต้องมีสูตร) · สคีมาแยกไว้ให้แล้ว (`price_delta` อยู่บน modifier,
  `qty_delta` อยู่คนละตาราง) แต่โค้ดมัดรวม · **ผลพลอยได้: `NON_STOCK` จะรับ modifier แบบคำสั่งได้ทันที**
  ซึ่งลบข้อเสียใหญ่สุดของการใช้ `NON_STOCK` ทิ้ง (วันนี้ `stockConsumption.ts:139` throw
  `MODIFIER_REQUIRES_RECIPE` และ readiness บล็อกที่ `productConfiguration.ts:398`)

**บั๊ก B — onboarding สอนตรงข้ามกับทิศทางของผลิตภัณฑ์**

- checklist ร้านอาหาร **3 ใน 4 ข้อพูดเรื่องสูตร/วัตถุดิบ** (`apps/web/i18n/th.ts:1629-1632`
  และ `apps/web/i18n/en.ts:1627-1630`)

### 3.8 วงจรบิลที่จะใช้ (ไม่ต้องแก้ lifecycle)


### เฟส 1 · ธง "หมดวันนี้" + ความพร้อมตามชนิดสินค้า (migration `9.55`)

**เป้าหมาย:** ร้านกดปิดเมนูได้ และทุกช่องทางเคารพธงนั้นพร้อมกัน

1. ตารางใหม่: ธงปิดขายชั่วคราวต่อ **(สินค้า x สาขา)** — ปิดที่สาขา A ต้องไม่ปิดสาขา B
   เก็บ: ใครปิด · เมื่อไร · เหตุผลสั้น ๆ (ไม่บังคับ) · เวลาที่จะรีเซ็ต
2. ตั้งค่าระดับร้าน: เวลารีเซ็ตรายวัน (**ค่าปริยาย 04:00 Asia/Bangkok** — ไม่ใช่เที่ยงคืน เพราะร้านอาหาร
   ขายข้ามเที่ยงคืนเป็นปกติ การรีเซ็ตตอนเที่ยงคืน = เปิดเมนูที่หมดกลับมาขายกลางรอบบริการ)
3. รีเซ็ตด้วย **สองสัญญาณ** — ทั้งคู่ยึด `resets_at` เป็นเกณฑ์เดียวกัน:
   - cron ตามเวลาที่ร้านตั้ง (ยิงทุก 15 นาที เพื่อเคารพ timezone/เวลารีเซ็ตของแต่ละร้าน)
   - เปิดกะที่สาขานั้น (`bms_pos_shifts`) เป็น **ตัวกวาดสำรอง** สำหรับร้านที่ยังไม่ได้ตั้ง cron
   (ต้องมีทั้งคู่ เพราะร้านที่ขายเดลิเวอรีล้วนอาจไม่เปิดกะ POS เลย)
   **⚠️ เปิดกะล้างได้แค่แถวที่ `resets_at` ถึงแล้ว ห้ามล้างทั้งสาขา** — กะเป็นของ "เครื่อง x คนขาย"
   ไม่ใช่ของ "วันบริการ" ร้านสองเครื่องหรือร้านที่เปลี่ยนกะกลางวันเปิดกะหลายรอบต่อวัน การล้างทั้งสาขา
   คือความเสียหายเดียวกับที่เหตุผลข้อ 2 กันไว้ (เปิดเมนูที่หมดกลับมาขายกลางรอบบริการ) แต่มาจาก
   การเปิดกะแทนที่จะมาจากเที่ยงคืน · แก้แล้วในรอบ recheck 2026-09-04
4. **ฟังก์ชันเดียวที่ตอบว่าเมนูขายได้ไหม** เช่น `isMenuSellable()` — ทุกช่องทางเรียกตัวนี้:
   AI · หน้าร้านออนไลน์ · จอสั่งอาหาร `/pos/restaurant` · เครื่องค้าปลีก `/pos`
   **ห้ามให้แต่ละหน้าจอเช็คเอง** ไม่งั้นวันหนึ่งจะเกิด "ปิดที่จอครัวแล้ว แต่แชทยังขายอยู่"
5. ความพร้อมตาม stock policy:

| policy | ตอบว่า |
|---|---|
| `NON_STOCK` | **ขายได้เสมอ** จนกว่าธงจะถูกกดปิด |
| `RECIPE` | เฟสนี้: ขายได้ แล้วให้ `createOrder` เป็นผู้ตัดสิน (มันตรวจวัตถุดิบจริงอยู่แล้ว) |
| `DIRECT`/`PACK` | ตามเดิม นับจากสต็อกจริง |

6. ปุ่มปิด/เปิดต้องอยู่ที่ **จอครัว** และ **หน้าขาย** (กดได้ใน 1 คลิก) ไม่ใช่ซ่อนในหน้าแก้ไขสินค้า
7. หน้าลูกค้า/AI ต้องบอกว่า **"วันนี้หมด"** ไม่ใช่ให้เมนูหายไปเฉย ๆ

**Acceptance**

- ปิดเมนูที่สาขา A → สาขา B ยังขายได้ · ทุกช่องทางของสาขา A ปฏิเสธพร้อมกัน
- ถึงเวลารีเซ็ต หรือเปิดกะ → เมนูกลับมาขายได้เอง
- ธงนี้ **ไม่แตะ `active`** — สินค้าที่ปิดชั่วคราวยังเป็นสินค้าที่เปิดขายอยู่

### เฟส 4 · ตัดรายการ + คืนส่วนต่าง (migration `9.57`)

**นี่คือเฟสที่ซับซ้อนที่สุด อ่านทั้งหัวข้อก่อนเขียนบรรทัดแรก**

#### 4.1 ใช้เครื่องยนต์เดิม อย่าสร้างที่สอง

ขยาย `processPosReturn()` (`apps/web/lib/bms/pos.ts:4094`) ให้รับ **`deviceId = null`**
แล้วเส้นทางออนไลน์เรียกตัวเดียวกัน → ได้ repricing + snapshot + idempotency + audit + ledger ครบทันที
· ต่างกันแค่ปลายทางของเงิน: POS = เงินสดจากลิ้นชัก · ออนไลน์ = โอนคืน (เข้าคิว)

**ห้ามเขียนเส้นทางออนไลน์ที่คำนวณยอดคืนเอง** — repo นี้เคย drift จากสูตรเงินสองชุดมาแล้วหลายรอบ

#### 4.2 สิ่งที่ต้องย้อนกลับ (วันนี้ทุกตัวเป็น "ทั้งบิล")

อ่าน `cancelOrderInTx` (`apps/web/lib/bms/orders.ts:1583`) เป็นรายการตั้งต้น:
reserved stock · movement `RELEASE` · ตั๋วครัว · คูปอง · คูปองที่จองไว้ · แต้ม · เครดิตร้าน ·
restock subscription — **ทุกตัวต้องตอบว่า "สัดส่วนเท่าไร"** ไม่ใช่แค่ลบแถวออก

#### 4.3 ราคาไม่ได้คิดรายบรรทัด

ตัด 1 รายการ **อาจทำให้รายการที่เหลือแพงขึ้น** — ราคาส่งตามจำนวน (`8.1`) นับรวมทั้งบิลต่อ SKU
และโปรโมชัน (`8.7`) คิดครั้งเดียวต่อ SKU ต่อบิล · ใช้ `priceRemainingLines()` เท่านั้น

#### 4.4 คูปอง — แยกตามต้นเหตุ

**เก็บ "ต้นเหตุ" ต่อรายการที่ถูกตัด: ร้าน (ของหมด) หรือ ลูกค้า (เปลี่ยนใจ)**

**ห้ามให้ต้นเหตุเป็น dropdown ล้วน** — มันเป็นตัวตัดสินเงิน ถ้าเลือกได้อิสระ คนหน้าเคาน์เตอร์จะกด
"ร้านของหมด" เสมอ เพราะลูกค้าไม่โวย → กฎไม่เคยทำงาน และรายงานเป็นตัวเลขขยะ

| สถานการณ์ | ต้นเหตุ |
|---|---|
| รายการนั้นถูกกดปิด "หมดวันนี้" ที่สาขานั้นอยู่ (เฟส 1) | **ร้าน — อัตโนมัติ** |
| ตัดโดยที่เมนูยังเปิดขายอยู่ | ต้องเลือก + บันทึกว่าใครเลือก · ถ้าเลือก "ของหมด" ให้ชวนกดปิดเมนูนั้นด้วย |
| ลูกค้าขอเปลี่ยนใจผ่านแชท | **ลูกค้า** |

**กฎเดียวที่ครอบทุกกรณีรวมถึงบิลที่มีสองต้นเหตุปนกัน:**

> ตรวจขั้นต่ำของคูปองกับ **ยอดของที่เหลือ + มูลค่าของที่ร้านเป็นเหตุให้หายไป**

ลูกค้าไม่ถูกลงโทษจากสิ่งที่ร้านส่งไม่ได้ แต่ยังถูกวัดตามปกติจากสิ่งที่ตัวเองยกเลิก

- ถ้าคูปองถูกถอด → **คืนโควตา** (`redemptions_count`) และคืนสิทธิ์เข้ากระเป๋าลูกค้า
  (`releaseCouponForOrdersInTx` / `releaseCustomerCouponReservationsInTx` มีอยู่แล้วแต่เป็นระดับบิล)
- "ราคาของต้องมากกว่าคูปอง" **บังคับอยู่แล้ว** ที่ `coupons.ts:113` และ `:937` (`Math.min(value, subtotal)`)
  — งานคือประเมินซ้ำ ไม่ใช่เพิ่มการ cap
- เครื่องยนต์เดิม **จงใจไม่แตะคูปอง** เมื่อคืนของบางส่วน (`pos.ts:4472` —
  *"ส่วนลดระดับบิลเดิม (สมาชิก/คูปอง/แต้ม/มือ) ยังคงตามสัดส่วนเดิม"*)
  → **การประเมินคูปองใหม่ต้องเป็นนโยบายที่ส่งเข้าไป ไม่ใช่เปลี่ยนพฤติกรรมกลาง**
  ไม่งั้นการคืนสินค้าที่เคาน์เตอร์ของทุกร้านเปลี่ยนไปด้วย
- **ต้นเหตุแก้ย้อนหลังไม่ได้** — แก้ทีหลัง = เปลี่ยนคำตอบว่าคูปองควรหลุดหรือไม่ หลังเงินออกไปแล้ว

#### 4.5 ร้านรับส่วนต่างเอง

- วันนี้ `REPRICE_PAYMENT_REQUIRED` ทำ `ROLLBACK` แล้วคืนสถานะ (`pos.ts:4497`)
  "ร้านรับเอง" = **เดินหน้าต่อโดยยอดคืนไม่ติดลบ** ไม่ใช่ซ่อน error
- **ต้องมีบรรทัดอธิบายส่วนต่าง** ไม่งั้นบิลบวกไม่ลงตัว (กฎของ `9.22`)
  → เก็บที่ `bms_order_discounts` แต่ `source` CHECK มีแค่ **4 ค่า**
  (`TIER/COUPON/POINTS/MANUAL`, `7.96:152`) → **ต้อง migration เพิ่มค่าที่ 5**
- **ห้ามยืม `MANUAL`** — ที่เคาน์เตอร์ส่วนลดมือต้องกด PIN คนที่สองเสมอ
  และรายงานส่วนลดมือจะกลายเป็นตัวเลขที่โกหกว่าใครเป็นคนให้ส่วนลด
- `UNIQUE (order_id, source)` → ตัดหลายรอบต้อง **บวกทับแถวเดิม** ไม่ใช่ INSERT ใหม่
- **เพดาน ฿2,000 (ตั้งได้ระดับร้าน)** เกินแล้วต้องให้ผู้จัดการยืนยันด้วย PIN ที่ `/pos`
  **ห้ามเรียก `approvalRuleForRefundAmount()`** (`pos.ts:3990`) — มันวัด *ยอดที่คืนให้ลูกค้า*
  ส่วนของใหม่วัด *ยอดที่ร้านกลืนเอง* คนละความหมาย เลขบังเอิญเท่ากัน · ต้องเป็นกฎแยก ชื่อแยก
- ต้องมี **รายงาน "เดือนนี้ร้านรับภาระไปเท่าไร จากเมนูไหน"** — ไม่มีรายงาน = ขาดทุนที่ไม่มีใครเห็น

#### 4.6 สิทธิ์และผู้กด

- **permission ใหม่** (เช่น `order.line.cancel`) — **seed ให้ Manager + Cashier ทุก tenant**
  แบบ migration `5.7` · ไม่ seed = ปุ่มโดน 403 เงียบ ๆ (403 ไม่เตะ logout, ดู `apollo.ts` errorLink)
- ห้าม grant `order.return` ให้ Cashier (ดูข้อ 3.7)
- **ไม่ต้องมีผู้อนุมัติที่สอง** สำหรับการตัดรายการ ไม่ว่ายอดเท่าไร
  (ยกเว้นเพดานส่วนต่างที่ร้านรับในข้อ 4.5)
- **audit ต้องอยู่ในทรานแซกชันเดียวกับการคืนเงิน** ระบุ: คนกด · ต้นเหตุ · รายการที่ตัด ·
  ยอดคืน · ยอดที่ร้านรับ · การเลือกไม่มีผู้อนุมัติที่สองทำให้ audit เป็นหลักฐานชิ้นเดียวที่เหลือ

#### 4.7 คิวคืนเงิน

- ใช้ `bms_pos_refund_allocations` + `completePosRefundAllocation()` ที่มีอยู่
- **ต้องสร้างหน้าจอ** — วันนี้ไม่มีที่ไหนแสดงคิวนี้เลย (ดูข้อ 3.4)
- คิวต้องแสดง: ยอด · ลูกค้าและช่องทางที่ต้องโอนคืน · ใครกดยกเลิกและเมื่อไร ·
  **ค้างมากี่ชั่วโมง** · ปุ่มปิดพร้อมเลขอ้างอิงการโอน (`externalRef`)
- อยู่ที่ `/pos` (แคชเชียร์เห็น) + กระจกเงาที่ `/admin` (ผู้จัดการกระทบยอด)

#### 4.8 อื่น ๆ ในเฟสนี้

- ปิดตั๋วครัว **รายรายการ** — วันนี้ `cancelKitchenTicketsForOrderInTx` เป็นทั้งบิล (`kitchen.ts:151`)
- คืนแต้มบางส่วน — `reversePointsForReturnInTx` บังคับ `posReturnId` (`membership.ts:853`)
  → ต้อง generalize (แต่ `bms_pos_returns` รองรับ `pos_device_id = NULL` อยู่แล้ว จึงสร้างแถวได้)
- **แจ้งลูกค้ากลับในห้องแชทเดิม** เมื่อร้านตัดรายการ/ปฏิเสธ — ห้ามให้ลูกค้ารู้ตอนอาหารมาไม่ครบ
  · ข้อความต้องอธิบายด้วยว่าทำไมคืนเงินไม่เท่ากับราคาของที่ตัด (เช่น คูปองถูกถอด)

**migration `9.57` ต้องมีอย่างน้อย 4 อย่าง**

1. ขยาย CHECK `bms_order_discounts.source` เพิ่มค่า "ร้านรับส่วนต่าง"

## 5. เทสที่ต้องมี

repo นี้แยกเป็น **pure** (ไม่ต้องมี DB) และ **`-db-contract`** (เขียนจริงลงฐาน)
· ทั้งสองชนิดต้อง **ผ่าน mutation test** ไม่ใช่แค่เขียว: ย้อนโค้ดกลับทีละจุดแล้วดูว่าแดงถูกตัว

**pure**

- `isMenuSellable()` ทุก policy x ปิด/ไม่ปิด x สาขา
- การรีเซ็ตตามขอบเขตวัน (04:00 ไม่ใช่เที่ยงคืน)
- แยกชนิด modifier (คำสั่ง vs วัตถุดิบ)
- "ยอดสมมติ" ของคูปองในบิลผสมสองต้นเหตุ — เหลือ 400 + ร้านเป็นเหตุ 100 = 500 → คูปองขั้นต่ำ 500 **อยู่ต่อ**
- เพดานร้านรับเอง: ฿1,999 ผ่าน · ฿2,001 ต้องมีผู้อนุมัติ · **และต้องไม่เรียก `approvalRuleForRefundAmount`**
- `ผลรวมรายการ + ส่วนลด + ส่วนต่างที่ร้านรับ = ยอดที่ลูกค้าจ่ายจริง` เสมอ

**DB contract**

- ปิดเมนู → **ทุกช่องทางปฏิเสธพร้อมกัน** (AI / ออนไลน์ / จอสั่งอาหาร / POS ค้าปลีก) และสาขาอื่นยังขายได้
- ตัดรายการที่เมนูถูกกดปิดอยู่ → ต้นเหตุเป็น "ร้าน" **อัตโนมัติ**
- ตัดเพราะลูกค้าเปลี่ยนใจจนต่ำกว่าขั้นต่ำ → คูปองถูกถอด **และโควตาคูปองถูกคืน**
- ตัด 1 จาก 5 ที่ได้ราคาส่ง → ราคาที่เหลือถูกประเมินใหม่จริง
- ตัดรายการ **สองรอบ** บนบิลเดียว → แถว `bms_order_discounts` ถูกบวกทับ ไม่ชน `UNIQUE (order_id, source)`
- Cashier ตัดรายการเดลิเวอรีได้ · **Cashier ยังคืนของทั้งบิลที่เคาน์เตอร์ไม่ได้** ← กันคนแก้ด้วยการ grant `order.return`
- ยกเลิกแล้วเกิดแถวคิวคืนเงินสถานะ `PENDING` และปิดด้วย `externalRef` ได้
- audit อยู่ในทรานแซกชันเดียวกับการคืนเงิน (บิลที่ rollback ต้องไม่ทิ้ง audit ค้าง)
- ตั๋วครัวของรายการที่ถูกตัดถูกปิด รายการอื่นไม่ถูกแตะ

**mutation test ที่ต้องยืนยันว่าแดงจริง**

- ทำให้ต้นเหตุเป็น dropdown ล้วนโดยไม่อนุมานจากธง
- ให้เพดานเรียกฟังก์ชันเพดานเดิม
- ทำให้ "ร้านรับเอง" เป็นพฤติกรรมกลาง (เส้นทางเคาน์เตอร์ต้องแดง)
- grant `order.return` ให้ Cashier แทน permission ใหม่
- ถอดการประเมินคูปองใหม่
- ย้ายปุ่มตัดรายการไป `/admin` อย่างเดียว

**กับดักของเทสแบบสแกนซอร์สใน repo นี้**: ต้องตัดคอมเมนต์ออกก่อนเทียบ ไม่งั้นคอมเมนต์ที่อธิบาย
กฎเก่าจะถูกจับเป็นของจริง (เคยเกิดแล้วหลายรอบ — ดู `withoutComments` ใน
`scripts/product-catalog-foundation-contract.test.mts`)

## 6. กับดักเฉพาะที่เคยทำให้พังมาแล้ว

1. **คีย์ i18n วางผิด section = โชว์ชื่อ key ดิบบนหน้าจอร้าน** — `getMessage()` คืน key ตัวเองเมื่อหาไม่เจอ
   `tsc` จับไม่ได้ · รัน `scripts/i18n-keys-contract.test.mts` เสมอ
2. **`/pos/page.tsx` เป็นภาษาไทย hardcode ทั้งหน้าโดยตั้งใจ** — หน้าใหม่ใน `/pos` เดินตามแบบเดิมได้
   แต่หน้าใน `/admin` ต้องผ่าน `t()` ครบทั้ง th/en
3. **เมนู sidebar ที่มี badge ต้องส่ง `collapsed` เสมอ**
4. **JSX**: ห้ามวางคอมเมนต์ `/* ... */` เป็น child แรกทันทีหลัง `{cond && (`
5. **อย่าใช้ regex ที่มี `.*?` ข้ามบรรทัดแก้ JSX** — เคยกลืน `<option>` ของคอมโพเนนต์อื่น
   แทนที่ด้วยสตริงตรง ๆ ทีละจุด แล้วให้ `tsc` เป็นตัวจับ
6. **`io.open(path,'w')` ของ Python บน Windows แปลง `\n` เป็น CRLF** — ตรวจ `git diff --stat`
   ทุกครั้งหลังแก้ด้วยสคริปต์
7. **`pg` คืน `DATE` เป็น `Date` ที่เที่ยงคืนเวลาท้องถิ่น** — `.toISOString().slice(0,10)` ถอยไป 1 วัน
   ในโซนไทย · cast `::text` ใน SQL แทน
8. **`Date` จาก `pg` ต้อง `.toISOString()` ก่อนคืนใน resolver ที่ field เป็น `String!`**
9. **เทสที่ต้องสลับ `business_archetype` ให้สร้าง tenant ของตัวเองเสมอ** — เคยทำร้านจริงค้างเป็น
   ร้านยาจนชุดเทส POS แดง 10 ตัว
10. **`test:db` เขียนจริงลงฐาน ห้ามรันกับ production**

## 7. Definition of done ของทุกเฟส

```bash
cd apps/web && npm run gate
```

```bash
cd apps/web && npm run test:db
```

- `npm run gate` (typecheck → pure tests → production build) ผ่านทั้งชุด
- เทส DB ที่เกี่ยวข้องผ่าน และ **รันซ้ำได้** (teardown ลบข้อมูลตัวเองครบ ยืนยัน 2 รอบ)
- mutation test ยืนยันว่าเทสใหม่แดงจริงเมื่อย้อนโค้ดกลับ
- migration apply เข้า dev DB จริงแล้ว (`psql -1`) และบันทึกสถานะไว้ใน `CLAUDE.local.md`
- เปิดดูหน้าจอจริงในเบราว์เซอร์ · ถ้าเปิดไม่ได้ **ต้องเขียนไว้ตรง ๆ ว่ายังไม่ได้เปิดดู**
  ห้ามรายงานว่าเสร็จโดยผ่านแค่ `tsc`
- อัปเดต `CLAUDE.local.md`: เลข migration · apply เข้า dev/production แล้วหรือยัง ·
  permission ใหม่ที่ต้อง seed · สิ่งที่ยัง verify ไม่ได้
