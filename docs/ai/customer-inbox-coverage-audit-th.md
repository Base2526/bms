# Recheck เส้นทางตอบ AI Inbox ตามคลังคำถามลูกค้า

ตรวจเทียบ [คลังคำถาม 440 ข้อ](customer-inbox-question-bank-th.md) กับ `customerTools(archetype)`, `pipeline.ts`, service ที่เครื่องมือเรียก, [AI guidelines](../AI_GUIDELINES.md) และ [กฎโดเมน](../agent-invariants.md) ใน branch นี้ ตารางครอบคลุม **ทุกหมายเลข**; ช่วงหมายเลขในแถวเดียวกันมีหลักฐานและข้อจำกัดเดียวกันหรือใกล้กัน การตรวจนี้เป็น **static capability/guard audit** ไม่ใช่ผลทดลองโมเดลกับข้อมูลร้านจริงหรือหลักฐานว่า production deploy แล้ว

รหัสผล: **R** มีเครื่องมืออ่านข้อเท็จจริง แต่ตอบได้เมื่อร้านกรอกและผลสดยืนยัน; **P** ตอบได้เพียงบางส่วน/ต้องถามเพิ่ม/ไม่รับรองผล; **W** มีเส้นทางทำงานที่ต้องมีสรุปล่าสุดและยืนยันตาม backend; **H** ต้องพนักงานหรือผู้เชี่ยวชาญตัดสินใจ; **N** ยังไม่มีเส้นทางอัตโนมัติที่ยืนยันคำขอนี้; **D** ต้องปฏิเสธการเปิดเผยหรือข้ามสิทธิ์; **E** เส้นทางฉุกเฉินคงที่ ข้อ R/P/W ไม่ได้แปลว่าโมเดลตอบถูกทุกครั้ง

## บทสนทนาต่อเนื่อง 50 กรณี

ตารางนี้เป็นการจับคู่ **ความเสี่ยงที่ต้องทดสอบ** กับทางป้องกันในโค้ด ไม่ใช่ผลผ่านของการยิงโมเดลทีละกรณี

| กรณีในคลัง | จุดตรวจที่ต้องผ่าน |
| --- | --- |
| 1-10 | `requestedItems`, product/pack resolution, pending choice state และการหมดอายุของตัวเลือก; ต้องถามเมื่อสินค้า/หน่วย/จำนวนไม่ชัด |
| 11-15 | quote fingerprint, confirmation freshness, idempotency และ post-write response failure; ห้ามสร้างออร์เดอร์ซ้ำ |
| 16-24 | tool failure, branch scope, missing store facts, result limit และ channel visibility; ห้ามใช้ข้อมูลเก่าหรือบอกว่า “ไม่มี” จากผลที่ถูกตัด |
| 25-29 | server-established identity, tenant context, RBAC, signed session, prompt injection และ human confirmation; ห้ามเผยข้อมูลของผู้อื่น |
| 30-38 | grounded price/shipping/payment/tax/pharmacy/food safety/restaurant availability; ไม่มีหลักฐานต้องตอบว่าไม่ทราบหรือส่งต่อ |
| 39-42 | booking confirmation/version, promotion eligibility, published prices; ห้ามใช้สรุปเก่าหรือแปลง null เป็นฟรี |
| 43-50 | ภาษา/ข้อความผิดรูป, intent switch, callback persistence, payment configuration, unknown warranty date, tenant isolation |

## สิ่งที่ยังพิสูจน์ไม่ได้จากการตรวจนี้

1. คำถาม R/P/W ทุกข้อยังต้องทดสอบกับ **tenant sandbox ที่กรอกข้อมูลอ้างอิง** แบบมี/ไม่มี/ขัดกัน และกับผู้ให้บริการโมเดลจริง; `npm run gate` ไม่ทำ live-model/DB test.
2. ไม่มีการทดสอบ provider ทั้ง 440 ข้อ, webhook ทุกช่องทาง หรือสิทธิ์ข้าม tenant ของฐานข้อมูลจริงใน audit นี้. ชุดทดสอบเดิมครอบบางเส้นทางลึก โดยเฉพาะร้านยา ร้านอาหาร และบอร์ดเกม; ผลนั้นไม่ทำให้ข้ออื่นผ่านเอง.
3. รายการ H/N เป็นข้อจำกัดของ AI Inbox ที่ตั้งใจให้ปลอดภัยหรือยังไม่มี workflow; การตอบว่า “ทำได้” โดยไม่มีผล service เป็นความผิดพลาด. ต้องมีข้อมูล/นโยบายร้านและผู้รับผิดชอบก่อนขยายเครื่องมือ.

## ช่องว่างที่ควรแก้ถัดไป

1. **ข้อมูลสาขาของร้านทั่วไป:** `check_stock` อ่านสาขาเริ่มต้นได้ แต่ AI ลูกค้าร้านที่ไม่ใช่ร้านอาหารไม่มี directory ที่คืน branch ID สำหรับเลือกสาขาอื่น ต้องออกแบบ public-safe branch lookup และตรวจ tenant/channel visibility ก่อนขยายคำตอบสต็อกข้ามสาขา.
2. **ข้อมูลนโยบาย/สเปกที่พิสูจน์ได้:** คำถาม P จำนวนมากต้องใช้ล็อตที่จะส่งจริง วันรับประกัน เงื่อนไขคืนสินค้า ตารางขนาด เอกสารมาตรฐาน หรือ cold chain ที่ร้านยังไม่ได้เผยแพร่เป็น field/tool เฉพาะ ห้ามให้โมเดลเติมเองจาก description อิสระ.
3. **ขั้นตอนที่ยังไม่มีในแชท:** 01:30, 02:19, 08:17 ต้องออกแบบ service และการยืนยันแยกกัน; ไม่ควรเพิ่ม prompt ที่บอกว่า “ทำได้” ก่อนมี transaction/idempotency/RBAC จริง.
4. **หลักฐานตอบจริง:** ทำ sandbox fixture และ live eval ตามข้อ R/P/W ทีละ archetype โดยเริ่มจากราคา/สต็อก/สาขา/ค่าส่ง/การยืนยันซ้ำ; บันทึก expected facts และห้ามตีความผล pure gate เป็นคำตอบที่ผ่าน provider.

## เกณฑ์รับรอบต่อไป

ทำ fixture สำหรับแต่ละ archetype ที่มีสาขา สินค้า variant/pack ราคา เงื่อนไข โปร นโยบาย และสถานะออร์เดอร์ที่ตรวจได้; รัน live-model corpus ของคำถาม R/P/W และ 50 บทสนทนาต่อเนื่อง; ตรวจคำตอบกับผล service, no-tool/handoff, tenant/RBAC, การยืนยันล่าสุด, duplicate และ rollback ก่อนอ้างว่าตอบได้ครบจริง
