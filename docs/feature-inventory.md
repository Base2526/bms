# ทะเบียนฟีเจอร์ BMS

> ปรับปรุง **6 ก.ย. 2026** · สเปกรายโดเมนอยู่ใน [business/](business/) · สถาปัตยกรรม [architecture/system.md](architecture/system.md)
>
> เอกสารนี้ตอบคำถามเดียว: **"ระบบทำอะไรได้บ้าง และอะไรที่พิสูจน์แล้วจริง ๆ"**
> ไม่ใช่คู่มือใช้งาน (ดู `/admin/manual`) และไม่ใช่สเปก (ดู `docs/business/`)

```
ลูกค้า → AI → CRM → ออร์เดอร์ → สต็อก → ชำระเงิน → จัดส่ง → แดชบอร์ด
```

BMS **ไม่ใช่แชทบอท** — AI ไม่เคยเขียน SQL และไม่เคยแตะฐานข้อมูลเอง เรียกได้แค่เครื่องมือที่ผ่านการอนุมัติ
ตรรกะธุรกิจอยู่ที่ `apps/web/lib/bms/*.ts` ที่เดียว แล้วทั้ง REST และ GraphQL ใช้ร่วมกัน

## คำที่ใช้บอกสถานะ

| สถานะ | ความหมาย |
| --- | --- |
| ✅ **พร้อมใช้** | เดินครบเส้นและมีเทสคุม |
| ⚙️ **ต้องตั้งค่าก่อน** | โค้ดพร้อม แต่ต้องเปิด/ผูก/ตั้ง secret ก่อน |
| 🧪 **ยังไม่พิสูจน์** | เขียนแล้ว ยังไม่เคยยิงกับของจริง |

**สถานะเป็นของ "ความสามารถ" ไม่ใช่ของ "โมดูล"** — การสร้างใบจัดส่งพร้อมใช้ ขณะที่การจองพัสดุกับ

คือคำโกหกที่บอกกับพนักงานหน้าเคาน์เตอร์

| **แยกบิล/รวมบิลข้ามโต๊ะ · จองโต๊ะ · บัตรคิว** | 📋 แบ่งจ่ายในบิลเดียวทำได้แล้ว แต่แยกบิลออกหลายใบ/รวมโต๊ะ ยังเป็นคนละโมดูล |
| **งานตั้งเวลา (cron) ทั้ง 7 ตัว** | ⚠️ ยังไม่ตั้ง `BMS_APP_BASE_URL` + `BMS_CRON_SECRET` → **ทุก job ข้ามตัวเองเงียบ ๆ** workflow ขึ้นเขียวแต่ไม่มีอะไรรัน · แต้มไม่หมดอายุ เมนูไม่รีเซ็ต |
| **migration บน production** | ⚠️ หลายไฟล์ยังไม่ apply — ต้องตรวจกับฐานจริงก่อนเชื่อเอกสาร |

## ก่อน go-live ต้องทำ

**env ที่ต้องตั้ง** (ไม่ตั้ง = production จะล้มดัง ๆ ซึ่งคือเจตนา):

- `JWT_SECRET` — เซ็น session + คุกกี้เข้าดูร้าน
- `BMS_SECRET_KEY` — hex 64 ตัว เข้ารหัส token ของช่องทางและ API key ของร้าน
- `BMS_CHECKOUT_SECRET` — หมุนเมื่อไหร่ ลิงก์ชำระเงินที่ส่งลูกค้าไปแล้วใช้ไม่ได้ทันทีทั้งหมด
- `BMS_APP_BASE_URL` + `BMS_CRON_SECRET` — ไม่ตั้ง = งานตั้งเวลาไม่ทำงานเลย
- `NEXT_PUBLIC_BASE_URL` ให้ตรงโดเมนจริง
- `BMS_ALLOW_FAKE_SEED` ต้อง**ปิด**บน production

**⚠️ ถ้า production เคยรันโดยไม่ตั้ง `BMS_SECRET_KEY`** — ต้อง**หมุนคีย์** ไม่ใช่ตั้งแล้วจบ
ใช้ `scripts/rotate-bms-secret-key.mts` (ค่าปริยาย dry-run) · ตรวจก่อนด้วย `scripts/check-bms-secret-key.mts`

**ตรวจว่าฐานพร้อม**: `scripts/check-schema-readiness.mts` (read-only) — บอกด้วยว่า "ถ้าไม่รันไฟล์นี้จะพังยังไง"

> ⚠️ **หลายฟีเจอร์อ่านคอลัมน์ใหม่กับทุกบิลของทุกร้าน** (`9.40` `9.51` `9.52` `9.55` `9.61`) —
> ลืม apply migration แล้ว deploy โค้ด = **ขายไม่ได้ทั้งระบบ ไม่ใช่แค่ร้านที่ใช้ฟีเจอร์นั้น**
> **apply migration ก่อน deploy เสมอ**

**อื่น ๆ**: ให้แอปต่อ DB ด้วย role non-superuser (RLS จึงมีผลกับ read) · ตั้ง password/TLS ให้ Redis

## ประเภทร้านที่รองรับ (13 แบบ)

มินิมาร์ท · แฟชั่น · ของใช้ในบ้าน · ความงาม · อาหารและเครื่องดื่ม · แกดเจ็ต · ค้าส่ง B2B ·
ของขวัญ/เทศกาล · **ร้านยา** · สัตว์เลี้ยง · วัสดุก่อสร้าง · **ร้านอาหาร** · อื่น ๆ

ประเภทร้าน **ล็อกหลังบิลจริงใบแรก** — ประวัติการขายจริงจะตรึงค่านี้ไว้ ไม่ให้คำแนะนำของ AI
และ checklist เริ่มต้นหลุดจากความเป็นจริงของธุรกิจ

## กฎที่ห้ามละเมิด (สรุป)

1. **AI ไม่เขียน SQL และไม่แตะฐานข้อมูลเอง** — เรียกได้แค่เครื่องมือที่ลงทะเบียน
2. **AI ไม่แต่งเลขสต็อก ราคา หรือเลขบิล** — ข้อเท็จจริงมาจากผลลัพธ์ที่สำเร็จของ backend เท่านั้น
3. **AI ไม่ตั้งราคา ขนาดแพ็ก หรือจำนวนชิ้นต่อหน่วย** — อ่านจากฐานฝั่งเซิร์ฟเวอร์เสมอ
4. **งานอ่อนไหว (ลบ/คืนเงิน/ยกเลิก/เปลี่ยนราคา/ปรับสต็อก) ต้องมีคนยืนยัน + มีสิทธิ์**
5. **บิลของลูกค้าไม่ถูกสร้างจนกว่าลูกค้าจะเห็นทุกรายการและตอบตกลง**
6. **AI ไม่ตอบด้วยข้อความว่าง** — turn ที่ไม่มีข้อความคือความล้มเหลวของระบบ ต้องแจ้งคนดูแล
7. **audit ของการเขียนที่แตะเงิน/สต็อก อยู่ในทรานแซกชันเดียวกับการเคลื่อนไหวนั้น**
8. **REST route ไม่ได้ปลอดภัยเพราะอยู่ใต้ `/api`** — `middleware.ts` กันแค่ `/admin/**`
   ทุก `/api/bms/*` ต้องตรวจสิทธิ์เอง และ **derive tenant จากฝั่งเซิร์ฟเวอร์**
9. **เงินมีสูตรเดียว** — จอพรีวิวกับเซิร์ฟเวอร์ต้องใช้ฟังก์ชันตัวเดียวกัน ต่างกันสตางค์เดียว
   บิลถูกทิ้งทั้งใบด้วย `PAYMENT_MISMATCH` โดยหน้าเคาน์เตอร์ไม่รู้สาเหตุ
